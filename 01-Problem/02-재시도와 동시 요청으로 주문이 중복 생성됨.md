# Problem: 02-재시도와 동시 요청으로 주문이 중복 생성됨

## 상황

커머스 주문 서비스에서 사용자가 결제 버튼을 누른 뒤 응답이 늦어지자 버튼을 다시 누르거나, 모바일 네트워크 오류로 클라이언트가 같은 요청을 재시도한다.

```java
@PostMapping("/orders")
public OrderResponse create(@RequestBody CreateOrderRequest request) {
    Order order = orderService.create(request.memberId(), request.productId(), request.quantity());
    return OrderResponse.from(order);
}

@Transactional
public Order create(Long memberId, Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.decreaseStock(quantity);

    Order order = Order.create(memberId, productId, quantity);
    return orderRepository.save(order);
}
```

물류 도메인에서도 같은 문제가 생긴다.

```text
출고 요청 API timeout
  → WMS client가 같은 request를 retry
  → 같은 주문에 대한 출고 지시가 2건 생성
  → 창고 작업자가 중복 피킹/패킹
```

핵심은 **서버가 같은 비즈니스 요청을 구분할 키 없이 매번 새 생성 요청으로 처리하는 구조**다.

---

## 관찰된 증거

사용자/운영 증상:

```text
- 사용자는 주문 버튼을 한 번 눌렀다고 말함
- DB에는 같은 member_id, product_id, amount, created_at 근접 주문이 2건 존재
- PG 결제 승인도 2건 발생하거나, 주문은 2건인데 결제는 1건만 존재
- CS에서 중복 주문 취소 요청 증가
```

로그:

```text
2026-07-04 21:10:01.103 INFO  requestId=7f1 POST /orders member=42 product=100
2026-07-04 21:10:01.411 WARN  requestId=7f1 client timeout before response
2026-07-04 21:10:01.620 INFO  requestId=8a9 POST /orders member=42 product=100 retry=true
2026-07-04 21:10:01.701 INFO  orderId=9101 created member=42 product=100
2026-07-04 21:10:01.888 INFO  orderId=9102 created member=42 product=100
```

DB 확인:

```sql
SELECT member_id, product_id, quantity, COUNT(*)
FROM orders
WHERE created_at >= now() - interval '10 minutes'
GROUP BY member_id, product_id, quantity
HAVING COUNT(*) > 1;
```

문제 흐름:

```text
client timeout / double click / retry
        ↓
같은 의도의 POST 요청이 2번 도착
        ↓
서버는 요청 간 동일성을 판단하지 못함
        ↓
각 요청이 별도 INSERT 수행
        ↓
중복 주문 / 중복 출고 / 중복 결제
```

---

## 의심 문제

가장 먼저 의심할 문제는 **멱등성 없는 생성 API**다.

```text
문제 이름:
재시도 가능한 생성 요청의 멱등성 부재

문제 유형:
중복 요청 방어 실패 + DB 유일성 제약 부재 또는 예외 처리 부재
```

단순히 버튼을 비활성화하는 프론트엔드 문제로 보면 안 된다. 네트워크 timeout, proxy retry, 모바일 재전송, 사용자의 새로고침처럼 같은 의도의 요청은 언제든 다시 들어올 수 있다.

---

## 원인

생성 API는 기본적으로 요청이 들어올 때마다 새 row를 만든다. 따라서 요청을 구분할 비즈니스 키나 멱등성 키가 없으면 서버는 다음 두 요청을 같은 의도로 판단할 수 없다.

```text
POST /orders { memberId: 42, productId: 100, quantity: 1 }
POST /orders { memberId: 42, productId: 100, quantity: 1 }

서버 관점:
  같은 요청의 재시도인가?
  사용자가 같은 상품을 2번 주문한 것인가?
  구분 불가
```

DB 유일성 제약 없이 애플리케이션에서만 중복을 검사해도 동시성 창이 생긴다.

```text
T1: SELECT existing order → 없음
T2: SELECT existing order → 없음
T1: INSERT order 9101
T2: INSERT order 9102
```

JPA에서는 Unique Key 위반을 잡으려 해도 flush 시점을 놓치면 catch 블록이 동작하지 않을 수 있다.

```text
save() 호출
  → 영속성 컨텍스트에 적재
  → method 정상 종료
  → commit 직전 flush
  → DB unique constraint 위반
  → service 내부 try-catch 바깥에서 예외 발생
```

---

## 확인 방법

먼저 중복이 진짜 같은 의도의 재시도인지, 정상적인 복수 주문인지 구분한다.

```text
1. client request id, idempotency key, trace id 존재 여부 확인
2. 같은 사용자/상품/금액/배송지/짧은 시간 간격의 주문 중복 확인
3. PG transaction id와 내부 order id 매핑 확인
4. DB unique constraint 또는 partial unique index 존재 여부 확인
5. DataIntegrityViolationException 처리 위치와 flush 시점 확인
```

판단 기준:

```text
같은 idempotency key로 여러 요청이 들어왔는데 order가 여러 개다
  → 멱등성 저장/조회 로직 실패

idempotency key 자체가 없다
  → 서버가 재시도와 신규 요청을 구분할 수 없는 설계 문제

unique constraint 위반이 500으로 노출된다
  → DB 최후 보루는 있으나 application 예외 변환이 부족
```

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| 프론트 버튼 비활성화 | 사용자 더블클릭 일부 완화 | 네트워크 재시도/서버 중복 요청은 막지 못함 |
| DB Unique Key | 중복 INSERT 최후 차단 | 어떤 컬럼 조합이 같은 요청인지 신중히 정해야 함 |
| Unique Key + flush + 예외 변환 | 중복을 도메인 예외로 안정 변환 | JPA flush 시점과 제약명 파싱 처리 필요 |
| Idempotency Key 저장 | 같은 요청 재시도에 기존 결과 반환 가능 | 키 저장소, TTL, parameter mismatch 검증 필요 |
| Pessimistic Lock | 중복 판단 구간 직렬화 | lock 대기, connection 점유 증가 |
| Redis 분산 락 | 다중 서버에서 특정 key 단위 직렬화 | 락 만료/장애 시 DB 제약 없으면 중복 가능 |

권장 구조:

```text
client
  └─ Idempotency-Key: UUID
        ↓
server transaction
  1. idempotency_key 테이블에 key INSERT
     - unique(key)
  2. 이미 존재하면 기존 order 결과 반환
  3. 없으면 order 생성
  4. key와 order_id 매핑 저장
  5. commit
```

DB 방어선:

```sql
CREATE TABLE idempotency_keys (
    idempotency_key varchar(255) PRIMARY KEY,
    request_hash varchar(64) NOT NULL,
    order_id bigint,
    created_at timestamptz NOT NULL
);
```

처리 흐름:

```text
요청 A: key=abc INSERT 성공 → order 생성 → key에 order_id 저장
요청 B: key=abc INSERT 실패 → 기존 key 조회 → 기존 order 반환
```

## 트레이드오프

이 문제의 핵심 트레이드오프는 **중복을 어디에서 막고, 재시도에 어떤 응답을 줄 것인가**다.

```text
Unique Key만 사용
  장점: 단순하고 강력한 최후 보루
  단점: 사용자는 기존 결과를 받기보다 중복 오류를 받을 수 있음

Idempotency Key 사용
  장점: 안전한 재시도와 기존 결과 반환 가능
  단점: key 저장소, request hash 검증, TTL 정책 필요

Lock 사용
  장점: 특정 구간을 직렬화해 중복 판단을 단순화
  단점: 경합이 커지면 latency와 connection 점유 시간이 증가
```

면접 답변에서는 다음 순서가 좋다.

```text
1. 중복 주문은 단순 프론트 더블클릭 문제가 아니라 재시도 가능한 생성 API의 멱등성 문제입니다.
2. 먼저 request id/idempotency key, 주문/결제 매핑, unique constraint 존재 여부를 확인하겠습니다.
3. DB Unique Key를 최후 보루로 두고, API에는 Idempotency-Key를 받아 같은 요청이면 기존 결과를 반환하게 하겠습니다.
4. JPA 환경에서는 unique 위반을 service 내부에서 잡으려면 flush 시점을 명확히 하거나 transaction 바깥 예외 변환 레이어를 둡니다.
5. lock은 중복 판단에 필요한 경우에만 쓰고, lock 단독이 아니라 DB 제약과 함께 둡니다.
```
