# Problem: 03-동시 요청으로 재고나 예약 수량 갱신이 소실됨

## 상황

예약, 재고, 신청 인원처럼 하나의 숫자를 여러 사용자가 동시에 바꾸는 API가 있다.

```java
@Transactional
public void apply(Long slotId, int passengerCount) {
    RentBoardingSlot slot = rentBoardingSlotRepository.findById(slotId)
        .orElseThrow();

    if (slot.getPassengerCount() + passengerCount > slot.getRecruitmentCount()) {
        throw new FullSlotException();
    }

    slot.increasePassengerCount(passengerCount);
}
```

코드만 보면 정원을 초과하지 않게 검사한 뒤 증가시키는 것처럼 보인다. 하지만 실제로는 `SELECT → 애플리케이션 메모리 계산 → UPDATE` 사이에 다른 트랜잭션이 끼어들 수 있다.

```text
요청 A: 현재 신청 인원 조회 → 0
요청 B: 현재 신청 인원 조회 → 0
요청 C: 현재 신청 인원 조회 → 0

각 요청이 메모리에서 0 + 1 계산
각 요청이 passenger_count = 1 저장

기대값: 3
실제값: 1
```

Allreva 차량 대절 신청 기능에서도 같은 구조가 있었다. k6로 100 VUs 동시 요청을 넣었을 때 모든 요청은 성공했지만 DB의 `passenger_count`는 16까지만 증가했다.

```text
# 문제 상황 — 모든 요청 200 OK, 하지만 DB는 손실
passenger_count: 16   (실제 신청자: 100명)
→ 84건의 갱신이 소멸

http_req_duration avg=784ms, p(95)=1.86s
```

---

## 관찰된 증거

대표 증상:

```text
- 성공 응답 수보다 DB의 재고/예약/신청 카운터 증가량이 작음
- 동시에 요청할수록 값이 더 많이 틀어짐
- 로그에는 각 요청이 정상 처리된 것처럼 보임
- 정원 초과 방어 로직이 있는데도 초과 신청 또는 누락 신청이 발생함
```

동시 실행 로그:

```text
[thread-1] current passengerCount: 0 → increment: 1
[thread-2] current passengerCount: 0 → increment: 1
[thread-3] current passengerCount: 0 → increment: 1
[thread-4] current passengerCount: 0 → increment: 1
[thread-5] current passengerCount: 0 → increment: 1
```

문제 흐름:

```text
T1: SELECT count=10 ── 계산 10+1 ───────── UPDATE count=11
T2: SELECT count=10 ─────── 계산 10+1 ─── UPDATE count=11

두 요청 모두 성공
하지만 최종 count는 12가 아니라 11
```

DB 관점에서는 두 트랜잭션이 같은 예전 값을 기준으로 새 값을 써버린다.

```text
read old value
   ↓
calculate in application memory
   ↓
write absolute value
   ↓
last writer wins
```

## 의심 문제

가장 먼저 의심할 문제는 **Read-Modify-Write 방식의 Lost Update**다.

```text
문제 이름:
동시 카운터 갱신의 Lost Update

문제 유형:
조회 값 기반 갱신 + 원자적 검증 부재 + 동시 요청 경합
```

핵심은 `@Transactional`이 붙어 있어도 `findById()`로 읽은 값과 나중의 `UPDATE`가 하나의 원자적 상태 전이로 보호되지 않는다는 점이다.

```text
@Transactional은 작업을 트랜잭션으로 묶음
하지만 읽은 값이 최신인지, 다른 요청이 중간에 바꿨는지는 자동으로 막아주지 않음
```

---

## 원인

JPA dirty checking 기반 증감은 보통 다음 SQL 흐름으로 바뀐다.

```sql
SELECT id, passenger_count, recruitment_count
FROM rent_boarding_slots
WHERE id = ?;

-- application memory에서 passenger_count + delta 계산

UPDATE rent_boarding_slots
SET passenger_count = ?
WHERE id = ?;
```

이 구조의 약점은 `UPDATE passenger_count = 11`처럼 계산 결과를 절대값으로 쓰는 데 있다. 같은 `10`을 읽은 요청이 여러 개면 모두 `11`을 저장한다.

```text
문제의 본질:
상태 검증과 상태 변경이 DB 안의 단일 연산으로 묶이지 않았다.
```

PostgreSQL의 Read Committed에서는 각 명령이 시작할 때의 snapshot을 본다. 그래서 단순한 `UPDATE count = count + 1 WHERE ...`는 같은 row를 갱신할 때 DB가 충돌을 조정할 수 있지만, 애플리케이션이 이전에 읽은 값을 기반으로 `UPDATE count = :calculatedValue`를 보내면 오래된 계산 결과로 덮어쓸 수 있다.

```text
좋은 갱신:
UPDATE slot SET passenger_count = passenger_count + 1 WHERE id = 1;

위험한 갱신:
SELECT passenger_count FROM slot WHERE id = 1; -- 10
UPDATE slot SET passenger_count = 11 WHERE id = 1;
```

## 확인 방법

먼저 성공 요청 수와 실제 DB 상태 변경량이 맞는지 확인한다.

```sql
-- 신청 row 수와 카운터 값 비교
SELECT s.id,
       s.passenger_count,
       COUNT(a.id) AS application_count
FROM rent_boarding_slots s
LEFT JOIN rent_applications a ON a.slot_id = s.id
WHERE s.id = :slotId
GROUP BY s.id, s.passenger_count;
```

동시 요청 테스트를 작게 재현한다.

```text
1. 같은 slotId에 대해 50~100개 동시 요청 전송
2. 모든 요청의 HTTP status와 business success count 기록
3. DB passenger_count 최종값 확인
4. 로그에서 여러 thread가 같은 current count를 읽었는지 확인
5. UPDATE SQL이 count = count + 1인지, count = ?인지 확인
```

Hibernate/JPA 환경에서는 SQL 로그를 켜서 dirty checking 결과를 확인한다.

```text
위험 신호:
update rent_boarding_slots
set passenger_count=?
where id=?

개선 신호:
update rent_boarding_slots
set passenger_count = passenger_count + ?
where id=? and passenger_count + ? <= recruitment_count
```

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| Atomic UPDATE | 단순 카운터 증감에 가장 단순하고 빠름 | 실패 원인을 rowCount로만 구분해야 함 |
| 낙관적 락 `@Version` | 기존 JPA 엔티티 모델과 잘 맞고 충돌 감지 가능 | 충돌 시 재시도/예외 처리 필요, 경합이 높으면 실패 증가 |
| 비관적 락 `SELECT FOR UPDATE` | 읽은 값 기반의 복잡한 판단을 보호 가능 | 대기 시간, deadlock, connection 점유 증가 |
| Serializable 격리 수준 | 트랜잭션 집합을 직렬 실행처럼 보장 | serialization failure 재시도와 성능 비용 필요 |
| 신청 row를 source of truth로 두고 count는 집계 | 정합성 기준이 명확함 | 매번 집계 비용 또는 별도 projection 동기화 필요 |

단순 수량 증감이면 우선 Atomic UPDATE로 바꾼다.

```sql
UPDATE rent_boarding_slots
SET passenger_count = passenger_count + :delta
WHERE id = :id
  AND passenger_count + :delta <= recruitment_count
  AND deleted_at IS NULL;
```

처리 결과는 `rowCount`로 판단한다.

```text
rowCount = 1 → 신청 성공
rowCount = 0 → 이미 마감됐거나 조건 불충족
```

JPA Repository 예시:

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("""
    update RentBoardingSlot s
       set s.passengerCount = s.passengerCount + :delta
     where s.id = :slotId
       and s.passengerCount + :delta <= s.recruitmentCount
       and s.deletedAt is null
""")
int increasePassengerCountIfAvailable(Long slotId, int delta);
```

화면에 보이는 잔여 수량은 오래될 수 있다. 대신 신청 시점에 DB 기준으로 다시 검증한다.

```text
목록 화면: 빠른 조회, stale read 허용
신청 API: Atomic UPDATE로 최종 검증
실패 시: "방금 마감되었습니다" 응답
```

## 트레이드오프

이 문제의 핵심 트레이드오프는 **정확한 동시성 제어를 어디까지 DB에 맡기고, 어디부터 애플리케이션 판단으로 가져올 것인가**다.

```text
Atomic UPDATE
  장점: count 증감과 상한 검증을 한 SQL로 묶음
  단점: 단순 조건에는 강하지만 복잡한 업무 판단에는 부족

Optimistic Lock
  장점: 충돌을 감지하고 재시도할 수 있음
  단점: 충돌이 잦으면 사용자는 실패/재시도를 많이 경험

Pessimistic Lock
  장점: 읽은 값 기반 판단을 안전하게 보호
  단점: lock 대기와 connection 점유가 생김
```

면접 답변에서는 다음 순서가 좋다.

```text
1. 성공 요청 수와 DB 카운터가 다르면 Lost Update를 의심합니다.
2. JPA의 find-modify-save가 SELECT와 UPDATE 사이 동시성 창을 만들었는지 SQL 로그로 확인합니다.
3. 단순 카운터 증감이면 Atomic UPDATE로 검증과 변경을 한 SQL에 넣고 rowCount로 성공/실패를 판단합니다.
4. 읽은 값으로 복잡한 결정을 해야 하면 optimistic lock 또는 SELECT FOR UPDATE를 검토합니다.
5. 화면의 잔여 수량은 stale할 수 있음을 허용하고, 최종 정합성은 신청 시점의 DB 검증으로 보장합니다.
```
