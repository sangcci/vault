# Problem: 33-스레드를 많이 만들었는데 처리량이 늘지 않고 문맥 교환만 증가함

## 상황

처리량을 높이기 위해 worker thread 수를 크게 늘렸다. 하지만 CPU 사용률은 높아지거나 들쭉날쭉하고, 실제 처리량은 기대만큼 오르지 않는다. 오히려 latency가 증가한다.

```text
CPU logical processor: 8개
worker thread: 500개

결과:
  동시에 실제 실행 가능한 단위는 8개
  나머지는 run queue에서 대기
  context switch 증가
```

---

## 관찰된 증거

- `vmstat`, `pidstat`, `/proc/PID/status`에서 context switch 수가 높다.
- run queue 길이가 CPU core 수보다 훨씬 크다.
- CPU profile에 실제 비즈니스 연산보다 scheduling/wait 비용이 많다.
- thread stack memory가 증가한다.
- lock 대기, I/O blocking thread가 많아지고 tail latency가 악화된다.

---

## 의심 문제

가장 가능성 높은 문제는 **소프트웨어 스레드 수를 늘리는 것과 실제 병렬 실행 능력을 혼동한 것**이다.

OS thread는 실행 가능한 작업 단위지만, 실제로 동시에 명령어를 실행하는 것은 hardware thread/logical processor 수에 제한된다.

---

## 원인

```text
Software Thread
  - OS가 스케줄링하는 실행 흐름
  - 수천 개 만들 수 있음

Hardware Thread
  - CPU가 동시에 실행할 수 있는 물리/논리 실행 슬롯
  - core/SMT 수로 제한됨

초과분
  - Ready queue에서 대기
  - timer interrupt마다 선점/복원
  - context switch 비용 발생
```

문맥 교환은 공짜가 아니다.

```text
현재 thread 상태 저장
  → 다음 thread 상태 복원
  → cache/TLB 영향
  → 실제 업무 연산이 아닌 관리 비용 증가
```

---

## 확인 방법

- logical CPU 수와 runnable thread 수를 비교한다.
- `/proc/PID/status`의 voluntary/nonvoluntary context switch를 확인한다.
- `top -H`, `pidstat -w`, `perf`, JVM thread dump로 thread 상태를 본다.
- 작업이 CPU-bound인지 I/O-bound인지 구분한다.
- thread pool 크기를 줄였을 때 latency와 throughput이 개선되는지 실험한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| CPU-bound pool을 core 수 근처로 제한 | context switch 감소 | blocking 작업과 분리 필요 |
| I/O-bound는 async/event loop 검토 | 대기 thread 감소 | 코드 모델 변화 |
| 작업 큐와 backpressure 도입 | 과도한 runnable 증가 방지 | 큐 지연 설계 필요 |
| thread pool 분리 | CPU/I/O 간섭 감소 | 설정 복잡도 증가 |
| lock contention 제거 | 대기/선점 감소 | 공유 상태 구조 변경 필요 |

---

## 트레이드오프

스레드는 동시성을 표현하는 편리한 단위지만, 실제 병렬성은 하드웨어 한도에 묶인다. 스레드를 늘리면 대기 작업을 숨길 수는 있지만, 일정 지점을 넘으면 스케줄러와 문맥 교환 비용이 처리량을 갉아먹는다.
