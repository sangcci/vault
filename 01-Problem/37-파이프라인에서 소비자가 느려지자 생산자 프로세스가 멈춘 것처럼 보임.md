# Problem: 37-파이프라인에서 소비자가 느려지자 생산자 프로세스가 멈춘 것처럼 보임

## 상황

큰 로그를 파이프라인으로 처리한다. 생산자는 계속 출력하는데 소비자가 느리거나 멈추면 생산자도 어느 순간 멈춘 것처럼 보인다.

```bash
cat huge.log | slow_filter | upload
```

```text
producer stdout → pipe buffer → consumer stdin

consumer 처리 지연
  → pipe buffer full
  → producer write() block
```

---

## 관찰된 증거

- 생산자 프로세스가 CPU를 거의 쓰지 않고 sleep 상태에 있다.
- 소비자를 멈추면 upstream 명령도 같이 멈춘다.
- 파이프 버퍼가 가득 찬 뒤 `write()`가 반환되지 않는다.
- `strace`에서 `write(fd, ...)`가 block되어 있다.
- 소비자가 읽기 시작하면 생산자가 다시 진행된다.

---

## 의심 문제

가장 가능성 높은 문제는 **커널 파이프의 유한 버퍼와 역압이 정상적으로 작동한 것**이다.

파이프는 무한한 메모리 큐가 아니라 제한된 커널 버퍼다. 소비자가 읽지 않으면 생산자는 더 이상 쓸 수 없고, 커널은 생산자를 대기시킨다.

---

## 원인

```text
pipe(fd)
  fd[1] = write end
  fd[0] = read end

producer write(fd[1])
  if buffer has space:
    copy bytes to kernel pipe buffer
  else:
    block or EAGAIN(O_NONBLOCK)

consumer read(fd[0])
  buffer에서 bytes 제거
  공간 생김 → producer wakeup
```

이 구조는 시스템을 보호한다.

```text
역압이 없으면:
  producer 속도 > consumer 속도
  → buffer 무한 증가
  → memory exhaustion / OOM

역압이 있으면:
  buffer full
  → producer를 멈춤
  → 처리 속도가 consumer에 수렴
```

---

## 확인 방법

- `strace -p <pid>`로 `write()` block 여부를 본다.
- downstream 프로세스가 실제로 읽고 있는지 확인한다.
- pipe 양 끝 fd가 불필요하게 열려 있어 EOF가 전달되지 않는지 확인한다.
- `O_NONBLOCK` 모드인지 확인한다.
- 중간 consumer의 buffer, flush, batch 정책을 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| downstream 처리 속도 개선 | 전체 처리량 증가 | 병목 원인 분석 필요 |
| batch 크기/flush 조정 | syscall/전송 비용 감소 | latency 증가 가능 |
| `O_NONBLOCK` + retry/poll | producer block 회피 | EAGAIN 처리 복잡 |
| bounded queue와 drop 정책 | OOM 방지 | 데이터 유실 정책 필요 |
| 사용하지 않는 fd close | EOF/종료 신호 정상화 | fork/dup2 구조 이해 필요 |

---

## 트레이드오프

파이프 역압은 멈춤처럼 보이지만 장애가 아니라 보호 장치다. 문제는 “왜 멈췄는가”가 아니라 “어느 소비자가 처리량을 제한하고, 멈춤을 대기·버림·재시도 중 어떤 정책으로 다룰 것인가”다.
