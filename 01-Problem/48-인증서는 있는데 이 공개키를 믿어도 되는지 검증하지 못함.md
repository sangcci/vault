# Problem: 48-인증서는 있는데 이 공개키를 믿어도 되는지 검증하지 못함

## 상황

서버가 공개키와 인증서를 제공한다. 하지만 클라이언트가 “이 공개키가 정말 해당 도메인의 것인지”, “중간에서 바꿔치기된 키는 아닌지” 검증하지 못하면 TLS를 써도 중간자 공격에 취약해진다.

```text
공격자 MITM
  client ── 공격자 공개키 ── attacker
  client는 암호화했다고 믿음
  하지만 공격자가 복호화 가능
```

---

## 관찰된 증거

- self-signed 인증서를 무조건 허용한다.
- hostname 검증을 끈다.
- 인증서 chain validation 실패를 무시한다.
- 인증서 만료/폐기 여부를 확인하지 않는다.
- 공개키 암호화와 “공개키 소유자 검증”을 같은 것으로 본다.

---

## 의심 문제

가장 가능성 높은 문제는 **암호화와 신뢰 검증을 분리하지 못한 것**이다.

공개키 암호화는 특정 공개키에 대해 안전한 통신을 만든다. 하지만 그 공개키가 누구의 것인지는 별도의 신뢰 체계가 필요하다. PKI는 CA 서명과 certificate chain으로 그 신뢰를 만든다.

---

## 원인

```text
전자서명
  데이터 hash
  private key로 signature 생성
  public key로 signature 검증
  → 무결성 + 서명자 인증 + 부인방지

PKI
  CA가 서버 인증서에 서명
  클라이언트는 root CA trust store에서 chain 검증
  hostname / validity / revocation 확인
  → 공개키 소유자 신뢰
```

---

## 확인 방법

- certificate chain이 trusted root까지 이어지는지 확인한다.
- hostname/SAN 검증이 켜져 있는지 확인한다.
- 만료 기간과 폐기 상태를 확인한다.
- 내부 서비스에서 self-signed를 쓴다면 trust anchor 관리가 명확한지 확인한다.
- 인증서 pinning을 쓴다면 rotation 전략이 있는지 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| 표준 TLS 검증 유지 | 기본 MITM 방어 | 개발 편의로 끄지 않기 |
| 사설 CA 운영 | 내부 서비스 신뢰 체계 구성 | CA 키 관리 부담 |
| 인증서 자동 갱신 | 만료 장애 감소 | 자동화 실패 감시 필요 |
| pinning 제한 사용 | 특정 공격면 감소 | 인증서 교체 시 장애 위험 |
| 폐기/만료 모니터링 | 운영 사고 예방 | 관측 체계 필요 |

---

## 트레이드오프

PKI는 신뢰 문제를 CA와 trust store에 위임해 인터넷 규모의 인증을 가능하게 한다. 대신 CA 침해, 인증서 만료, 잘못된 예외 허용이 전체 신뢰 체계를 무너뜨릴 수 있다.
