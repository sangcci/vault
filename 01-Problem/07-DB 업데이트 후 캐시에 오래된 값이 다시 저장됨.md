# Problem: 07-DB 업데이트 후 캐시에 오래된 값이 다시 저장됨

## 상황

조회 성능을 위해 캐시를 붙인 뒤, 수정 API에서 DB를 갱신하고 캐시를 비운다.

```java
@Transactional
public void updateProduct(Long id, UpdateRequest request) {
    cache.evict("product", id);
    productRepository.update(id, request);
}
```

겉보기에는 “수정 시 캐시 삭제”라서 안전해 보이지만, 트랜잭션 commit 전에 캐시를 먼저 비우면 동시 read가 오래된 DB 값을 다시 캐시에 넣을 수 있다.

---

## 관찰된 증거

```text
T1: 상품 수정 트랜잭션 시작
T1: cache evict(product:1)

T2: 상품 조회 요청
T2: cache miss
T2: DB old value 조회       ← T1 commit 전이라 old value가 보임
T2: cache put(product:1, old)

T1: DB commit new value

결과:
DB    = new
cache = old
```

증상은 다음처럼 나타난다.

- 수정 API는 성공했는데 조회 API는 이전 값을 반환한다.
- TTL이 만료되거나 수동 evict를 하기 전까지 오래된 값이 유지된다.
- 로그상 DB 업데이트와 캐시 evict는 모두 성공한 것처럼 보인다.

---

## 의심 문제

가장 가능성 높은 문제는 **DB 트랜잭션 경계와 캐시 무효화 타이밍이 어긋난 것**이다.

캐시와 DB는 별도 저장소이므로, 둘의 변경을 하나의 원자적 작업처럼 가정하면 stale cache가 생긴다.

---

## 원인

문제의 핵심은 “캐시를 비웠다”가 아니라 “언제 비웠는가”다.

```text
위험한 순서
cache evict
  ↓
동시 read가 old DB 값 조회
  ↓
old value cache put
  ↓
DB commit
```

캐시 무효화는 DB commit 이후에 실행되어야 stale window를 줄일 수 있다. 다만 commit 이후 evict도 완전한 분산 트랜잭션은 아니므로, DB와 캐시 사이의 일관성은 항상 시간차를 가진다.

---

## 확인 방법

- 수정 로직에서 `@CacheEvict`, `cache.evict()`, `@CachePut`이 트랜잭션 commit 전 실행되는지 확인한다.
- 수정 요청과 조회 요청을 동시에 발생시켜 stale cache 재현 테스트를 만든다.
- 캐시 값과 DB 값을 같은 key 기준으로 비교하는 운영 진단 로그를 남긴다.
- Spring Cache를 쓴다면 transaction-aware cache 설정 여부를 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| afterCommit 이후 evict | DB commit 전 old value 재저장 가능성 감소 | commit 이후 짧은 stale window는 남음 |
| TransactionAwareCacheManagerProxy | Spring 트랜잭션과 cache put 타이밍 동기화 | 모든 캐시 일관성 문제를 해결하지는 않음 |
| Cache-Aside / DB 우선 쓰기 | DB를 정답 원천으로 유지 | cache miss 순간 부하 증가 가능 |
| 짧은 TTL | 오래된 값 유지 시간 제한 | hit rate 감소 |
| 이벤트 기반 무효화 | 여러 인스턴스 캐시 동기화 가능 | 이벤트 유실/중복 처리 필요 |

---

## 트레이드오프

강한 일관성을 원하면 캐시의 단순성과 성능 이점을 잃기 쉽다. 반대로 캐시를 적극적으로 쓰면 일부 stale read와 무효화 지연을 설계상 받아들여야 한다.

따라서 캐시는 DB의 대체 저장소가 아니라 **읽기 최적화 복제본**으로 보고, 수정 경계에서는 “DB commit 이후 어떤 순서로 캐시를 무효화할 것인가”를 명시해야 한다.
