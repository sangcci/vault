# Problem: 08-캐시 만료 순간 같은 DB 조회가 동시에 몰림

## 상황

인기 조회 API에 캐시를 적용했다. 평소에는 응답이 빠르지만, 특정 시점마다 DB 부하가 순간적으로 튄다.

```java
@Cacheable(cacheNames = "popularProducts", key = "'top10'")
public List<ProductResponse> findPopularProducts() {
    return productRepository.findTop10();
}
```

TTL 만료, 수동 evict, 서버 재시작 직후에 같은 key를 찾는 요청이 동시에 들어오면 모든 요청이 cache miss를 맞고 같은 DB 조회를 반복 실행한다.

---

## 관찰된 증거

```text
cache key expired
  ↓
request 1 -> cache miss -> DB query
request 2 -> cache miss -> DB query
request 3 -> cache miss -> DB query
...
request N -> cache miss -> DB query
```

운영 증상은 다음과 같다.

- 캐시 hit rate는 평균적으로 높지만 특정 순간 DB QPS가 급증한다.
- 같은 SQL이 짧은 시간에 반복 실행된다.
- DB connection pool 사용량과 API tail latency가 함께 튄다.
- TTL이 같은 key들이 같은 시각에 만료되면 spike가 더 커진다.

---

## 의심 문제

가장 가능성 높은 문제는 **Cache Stampede**다.

캐시가 있는지 없는지만 보면 놓치기 쉽다. 핵심은 cache miss 순간에 “누가 원본 조회를 수행하고, 나머지 요청은 무엇을 하는가”다.

---

## 원인

캐시는 hit일 때 원본 저장소 부하를 줄인다. 하지만 miss가 동시에 발생하면 캐시는 부하 흡수 장치가 아니라 부하 집중 지점이 된다.

```text
캐시 HIT 상태
요청 N개 -> cache 1개 조회 -> DB 0회

캐시 동시 MISS 상태
요청 N개 -> cache miss N회 -> DB N회
```

특히 정형 key가 적고 트래픽이 몰리는 API일수록 stampede 위험이 크다. 캐시 key를 잘 잡아 hit rate를 높였더라도, 만료 시점 제어가 없으면 원본 저장소가 순간 부하를 맞는다.

---

## 확인 방법

- 같은 cache key에 대해 miss가 동시에 몇 번 발생하는지 로그로 확인한다.
- TTL 만료 시점과 DB QPS spike가 겹치는지 본다.
- `@Cacheable(sync = true)` 또는 request coalescing 적용 전후 DB query 수를 비교한다.
- 캐시 key별 hit/miss, load time, eviction 수를 분리해서 본다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| `@Cacheable(sync = true)` | 같은 key 계산을 한 스레드로 제한 | 대기 요청의 tail latency 증가 |
| Request Coalescing | 동일 key 원본 조회 중복 제거 | 구현 복잡도 증가 |
| TTL Jitter | 만료 시점 분산 | 만료 예측 어려움 |
| Soft TTL / Background Refresh | 사용자 요청 전에 갱신 | 백그라운드 작업 관리 필요 |
| Stale-While-Revalidate | 장애/부하 순간에도 응답 가능 | 잠깐 오래된 값 노출 |

---

## 트레이드오프

동시 miss를 막으려면 일부 요청을 기다리게 하거나 stale value를 허용해야 한다. 즉, cache stampede 대응은 “항상 최신 값”과 “원본 저장소 보호” 사이의 선택이다.

트래픽이 높은 읽기 API라면 캐시 적용 여부보다 **miss 시나리오**를 먼저 설계해야 한다.
