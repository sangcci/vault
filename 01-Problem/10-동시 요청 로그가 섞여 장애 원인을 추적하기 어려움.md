# Problem: 10-동시 요청 로그가 섞여 장애 원인을 추적하기 어려움

## 상황

운영 환경에서 여러 요청이 동시에 처리된다. 에러 로그는 남아 있지만, 어떤 사용자의 어떤 요청 흐름에서 발생한 실패인지 이어 붙이기 어렵다.

```text
[Thread-7] INFO  주문 시작 userId=A
[Thread-3] INFO  주문 시작 userId=B
[Thread-7] DEBUG 재고 확인
[Thread-3] DEBUG 결제 처리
[Thread-7] ERROR 결제 실패
[Thread-3] INFO  주문 완료
```

스레드 이름과 시간은 보이지만, 장애 원인을 재구성하기에는 요청 단위 맥락이 부족하다.

---

## 관찰된 증거

- 같은 시각에 여러 요청 로그가 섞여 있다.
- 에러 로그 한 줄은 있지만 앞뒤 비즈니스 흐름을 찾기 어렵다.
- 비동기 작업이나 다른 서비스 호출로 넘어가면 requestId가 끊긴다.
- 로그 저장소에서 `userId`, `orderId`, `traceId` 같은 필드로 필터링할 수 없다.

```text
장애 분석자가 하고 싶은 일
traceId=abc 요청만 필터링
  ↓
API Gateway → OrderService → PaymentService → DB
  ↓
어느 구간에서 실패했는지 재구성
```

---

## 의심 문제

가장 가능성 높은 문제는 **요청 흐름을 식별하는 correlation id/trace id가 로그와 호출 경계에 일관되게 전파되지 않은 것**이다.

로그가 많아도 요청 단위로 묶을 수 없으면 관측 신호가 아니라 문자열 더미가 된다.

---

## 원인

멀티스레드 서버에서는 로그가 시간순으로 하나의 파일에 모인다. 하지만 시간순은 요청순이 아니다.

```text
동시 요청 A/B/C
  ↓
스레드 풀에서 섞여 실행
  ↓
공유 로그 스트림에 append
  ↓
요청 식별자 없으면 흐름 재구성 불가
```

MDC 같은 스레드 로컬 기반 방식은 동기 흐름에서는 편하지만, 스레드 풀 재사용과 비동기 실행에서는 명시적 정리와 전파가 필요하다. MSA에서는 HTTP header로 trace context를 넘겨야 서비스 경계를 넘어 흐름이 이어진다.

---

## 확인 방법

- 모든 로그에 `traceId` 또는 `requestId`가 포함되는지 확인한다.
- 요청 진입 Filter/Interceptor에서 ID 생성 후 종료 시 MDC를 clear하는지 본다.
- `@Async`, `CompletableFuture`, scheduler, message consumer에서 context가 전파되는지 확인한다.
- 외부 HTTP 호출에 `traceparent` 또는 내부 correlation header가 전달되는지 확인한다.
- 로그가 JSON/key-value 형태로 저장되어 필드 검색이 가능한지 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| MDC + 구조화 로그 | 단일 서비스 요청 흐름을 필드로 추적 가능 | clear 누락, 비동기 전파 누락 위험 |
| Trace Context header 전파 | 서비스 간 요청 흐름 연결 | 모든 client/server 계층에 전파 구현 필요 |
| OpenTelemetry 도입 | trace/span 표준화, 도구 연동 | 초기 설정과 샘플링 정책 필요 |
| 로그 필드 표준화 | 검색/집계 품질 향상 | 팀 합의와 운영 규칙 필요 |
| 민감정보 마스킹 | 로그 유출 리스크 감소 | 디버깅 정보가 일부 줄어듦 |

---

## 트레이드오프

로그를 많이 남기는 것과 추적 가능한 로그를 남기는 것은 다르다. 운영에서는 로그 양보다 **요청을 재구성할 수 있는 최소 필드**가 더 중요하다.

따라서 `traceId`, `spanId`, `userId`, `endpoint`, `status`, `elapsed` 같은 필드를 표준화하고, 민감정보는 남기지 않는 쪽으로 설계해야 한다.
