# Problem: 23-운영 중 인덱스 추가로 쓰기 요청이 막히거나 마이그레이션이 멈춤

## 상황

운영 중인 대용량 테이블에 인덱스를 추가하려고 일반 `CREATE INDEX`를 실행했다. 이후 INSERT/UPDATE/DELETE 요청이 대기하면서 API 응답이 급격히 느려진다.

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

이를 피하려고 `CREATE INDEX CONCURRENTLY`를 사용했지만, Flyway 마이그레이션에서 끝나지 않고 대기하는 경우도 있다.

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders(user_id);
```

---

## 관찰된 증거

```text
일반 CREATE INDEX
  → 강한 테이블 잠금
  → DML 대기
  → 커넥션 점유 증가
  → API 지연/타임아웃

CREATE INDEX CONCURRENTLY + Flyway 설정 오류
  → SQL 자체 transaction은 제거
  → flyway_schema_history 잠금 transaction은 남음
  → concurrent index build가 기존 transaction 종료를 기다림
  → 자기 자신을 기다리는 형태로 장시간 대기
```

증상은 다음과 같다.

- 인덱스 생성 중 쓰기 요청 latency가 급증한다.
- `pg_locks`에서 인덱스 생성 작업과 DML이 서로 대기한다.
- `CONCURRENTLY`인데도 완료되지 않고 장시간 멈춘다.
- 실패 후 `INVALID` 인덱스가 남아 재시도도 꼬인다.

---

## 의심 문제

가장 가능성 높은 문제는 **운영 DDL의 잠금 모드와 트랜잭션 대기 조건을 고려하지 않은 것**이다.

일반 인덱스 생성은 빠를 수 있지만 writer를 막는다. `CONCURRENTLY`는 writer를 허용하지만 두 번 스캔하고, 기존 트랜잭션이 끝나기를 기다리며, 트랜잭션 블록 안에서 실행할 수 없다.

---

## 원인

```text
일반 CREATE INDEX
  ├─ 더 빠름
  └─ writer block 가능

CREATE INDEX CONCURRENTLY
  ├─ normal operation 계속 가능
  ├─ table scan 2회
  ├─ 기존 변경 transaction 종료 대기
  ├─ transaction block 안에서 실행 불가
  └─ 실패 시 INVALID index 남을 수 있음
```

Flyway에서는 `executeInTransaction=false`만으로 충분하지 않을 수 있다. SQL 래퍼 트랜잭션은 제거되지만, PostgreSQL advisory lock이 transaction 기반이면 별도 트랜잭션이 남아 `CONCURRENTLY`가 그것을 기다릴 수 있다.

---

## 확인 방법

- 운영 테이블 크기와 쓰기 트래픽이 있는지 확인한다.
- 일반 `CREATE INDEX`인지 `CREATE INDEX CONCURRENTLY`인지 확인한다.
- Flyway 사용 시 `executeInTransaction=false`와 `postgresql.transactional-lock=false`를 함께 확인한다.
- `pg_locks`, `pg_stat_activity`에서 대기 중인 PID와 blocking PID를 확인한다.
- 실패 후 `INVALID` 인덱스가 남았는지 확인하고 `DROP INDEX CONCURRENTLY`로 정리한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| `CREATE INDEX CONCURRENTLY` | writer block 최소화 | 더 오래 걸림, transaction block 불가 |
| 점검 시간 일반 `CREATE INDEX` | 빠르고 단순 | 운영 쓰기 중단 필요 |
| Flyway transaction lock 해제 | 자기 대기 방지 | 설정 검증 필요 |
| long transaction 사전 종료 | 대기 시간 단축 | 운영 영향 조율 필요 |
| 실패 인덱스 정리 후 재시도 | catalog 오염 방지 | 수동 운영 절차 필요 |

---

## 트레이드오프

운영 DDL은 “DDL 하나 실행”이 아니라 서비스 쓰기 흐름과 잠금 충돌을 같이 바꾸는 작업이다. `CONCURRENTLY`는 무중단에 가깝게 만들지만, 더 많은 시간·I/O·운영 절차를 요구한다.
