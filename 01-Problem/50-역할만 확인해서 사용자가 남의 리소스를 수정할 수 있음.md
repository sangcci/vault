# Problem: 50-역할만 확인해서 사용자가 남의 리소스를 수정할 수 있음

## 상황

API에서 `ROLE_USER`만 있으면 예약, 게시글, 주문 같은 리소스를 수정할 수 있게 했다. 사용자가 URL의 id만 바꾸면 다른 사용자의 리소스도 수정된다.

```http
PATCH /reservations/123
Authorization: ROLE_USER

# 123이 내 예약인지 확인하지 않음
```

---

## 관찰된 증거

- URL path id를 바꾸면 다른 사용자 데이터에 접근 가능하다.
- Spring Security나 gateway에서는 role만 검사한다.
- 서비스 로직에서 ownerId, tenantId, membership을 확인하지 않는다.
- 목록 조회에는 userId 필터가 있지만 단건 수정/삭제에는 없다.
- 관리자/사용자 role만으로 모든 인가를 표현하려 한다.

---

## 의심 문제

가장 가능성 높은 문제는 **인증된 사용자 역할과 리소스별 접근 권한을 혼동한 것**이다.

RBAC는 “이 사용자가 일반 사용자/관리자인가” 같은 정적 역할을 판단하기 좋다. 하지만 “이 사용자가 이 리소스의 소유자인가”, “이 팀의 멤버인가”는 리소스와 사용자 사이의 관계를 확인해야 한다.

---

## 원인

```text
RBAC
  subject → role → permission
  예: ROLE_ADMIN은 /admin 접근 가능

DAC / Ownership
  resource.ownerId == currentUser.id
  예: 내 예약만 수정 가능

ReBAC
  subject --relation--> resource
  예: 이 프로젝트의 maintainer만 배포 가능
```

보안 실패는 보통 coarse-grained check만 있고 object-level check가 빠질 때 생긴다.

---

## 확인 방법

- 모든 단건 조회/수정/삭제 API에서 object ownership을 확인한다.
- 목록 API의 필터와 단건 API의 검증이 일관적인지 본다.
- tenantId, organizationId, project membership 같은 관계 조건을 누락하지 않았는지 확인한다.
- deny-by-default 정책으로 조건이 없으면 거부하는지 확인한다.
- 테스트에서 다른 사용자 id로 접근하는 negative case를 넣는다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| RBAC + ownership check | 단순하고 현실적 | 서비스별 반복 가능 |
| query 단계에서 userId/tenantId 필터 | 데이터 노출 방지 | 누락 시 위험 |
| domain policy로 권한 판단 집중 | 규칙 일관성 | 설계 비용 |
| ReBAC 모델 도입 | 복잡한 관계 표현 | 쿼리/운영 복잡도 |
| deny-by-default | 누락 방어 | 명시적 허용 관리 필요 |

---

## 트레이드오프

역할 기반 인가는 관리가 쉽지만 리소스별 관계를 표현하지 못한다. 관계 기반 인가는 정확하지만 쿼리와 모델이 복잡해진다. 실무에서는 URL/메서드 레벨 RBAC와 도메인 객체 레벨 소유권 검사를 함께 둔다.
