# Problem: 55-코드 배포와 DB 스키마 변경 순서가 맞지 않아 장애가 발생함

## 상황

새 코드가 `users.phone` 컬럼을 읽도록 배포됐지만 운영 DB에는 아직 컬럼이 없다. 반대로 컬럼을 먼저 삭제했는데 구버전 애플리케이션이 아직 그 컬럼을 읽고 있어 장애가 난다.

```text
Code v2 expects column phone
DB schema is still v1
→ Column not found
```

---

## 관찰된 증거

- dev/stage/prod의 스키마 상태가 다르다.
- 적용된 migration 파일을 수정해 checksum 오류가 난다.
- 롤백하면 코드만 돌아가고 DB 상태는 그대로 남는다.
- 큰 테이블 ALTER가 운영 중 lock을 잡는다.

---

## 원인

코드는 쉽게 되돌릴 수 있지만 DB schema는 이미 변경된 상태가 남는다. Flyway 같은 도구는 migration 이력을 순서대로 한 번만 적용해 schema drift를 막지만, 배포 순서와 하위 호환성 설계는 별도로 필요하다.

---

## 해결 방향

- 적용된 versioned migration은 수정하지 않고 새 migration으로 fix-forward한다.
- schema 변경은 expand-contract로 나눈다.
  - nullable column 추가
  - 새 코드 배포
  - backfill
  - NOT NULL/삭제 같은 contract는 마지막에 수행
- JPA `ddl-auto`는 운영에서 schema 생성이 아니라 validate 중심으로 둔다.
- 대형 테이블 변경은 lock 영향과 online DDL 전략을 먼저 검토한다.
