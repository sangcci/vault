# Problem: 68-프로젝트를 기능 나열로만 설명해 기술 선택의 깊이가 드러나지 않음

## 상황

포트폴리오나 면접에서 “로그인 구현, 게시판 구현, 결제 API 연동”처럼 기능 목록만 설명한다. 면접관은 실제로 어떤 문제를 만났고, 어떤 기준으로 선택했으며, 무엇을 포기했는지 알 수 없다.

```text
나쁜 설명
  Redis를 사용했습니다.

좋은 설명
  중복 주문을 막기 위해 요청 멱등키를 Redis에 저장했습니다.
  TTL을 둬 저장 비용은 줄였지만, TTL 이후 재시도는 DB unique key로 한 번 더 방어했습니다.
```

---

## 관찰된 증거

- 사용 기술은 많은데 왜 선택했는지 설명하지 못한다.
- “성능 개선”이라고 말하지만 Before/After 수치가 없다.
- 장애/트러블슈팅 경험이 현상-원인-해결-배운점으로 정리되어 있지 않다.
- 회사 공고의 문제와 내 프로젝트 경험이 연결되지 않는다.
- 면접 답변이 일반론으로 흐른다.

---

## 원인

실무 역량은 기능 목록보다 상황, 제약, 기준, 선택, 트레이드오프를 통해 드러난다. 문서화는 코드를 예쁘게 설명하는 작업이 아니라 의사결정의 증거를 남기는 작업이다.

---

## 해결 방향

- 프로젝트마다 문제 상황, 선택 기준, 대안, 결과 수치를 남긴다.
- 트러블슈팅은 현상 → 원인 추론 → 해결 → 재발 방지로 쓴다.
- 면접 답변은 상황 → 기준 → 선택 → 트레이드오프 순서로 말한다.
- 채용공고는 기술 스택 목록이 아니라 회사가 겪는 문제의 힌트로 읽는다.
- 문서에는 ERD/API/아키텍처 그림보다 “왜 그렇게 했는가”를 함께 둔다.
