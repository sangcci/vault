# Problem: 11-대시보드 알람은 울렸지만 실제 병목 지점을 찾기 어려움

## 상황

Grafana 대시보드에서 p99 latency 알람이 울렸다. Prometheus에는 CPU, memory, request latency, error rate가 있고, Loki에는 애플리케이션 로그가 있다.

하지만 알람 이후 실제 원인이 DB인지, GC인지, 외부 API인지, 특정 endpoint인지 빠르게 좁혀지지 않는다.

---

## 관찰된 증거

```text
14:03 p99 latency spike
14:03 GC pause 증가
14:04 DB connection usage 증가
14:04 ERROR log 증가
14:05 CPU usage 증가
```

문제는 지표가 없는 것이 아니라, 서로 연결되어 있지 않은 것이다.

- metrics는 “얼마나 많이/느리게”를 보여주지만 요청 맥락이 부족하다.
- logs는 “무슨 일이 있었는지”를 보여주지만 전체 규모와 추세를 보기 어렵다.
- traces는 “어느 구간이 느린지”를 보여주지만 샘플링과 전파가 필요하다.

---

## 의심 문제

가장 가능성 높은 문제는 **관측 신호를 상관관계로 읽는 기준이 없는 것**이다.

도구는 설치되어 있지만, metrics → logs → traces로 이어지는 진단 흐름이 없으면 장애 대응은 다시 grep과 추측으로 돌아간다.

---

## 원인

옵저버빌리티는 도구 목록이 아니라 내부 상태를 외부 신호로 추론하는 능력이다.

```text
Metrics: 이상 감지
  ↓
Logs: 이벤트 맥락 확인
  ↓
Traces: 느린 구간 확인
  ↓
Hypothesis: DB / GC / 외부 API / lock / connection pool
  ↓
Verification: 같은 시간축에서 재확인
```

각 신호가 시간, 서비스, endpoint, traceId 같은 공통 축을 공유하지 않으면 연결이 끊긴다.

---

## 확인 방법

- 대시보드가 endpoint, status, service, instance 기준으로 drill-down 가능한지 확인한다.
- latency spike 시점의 log를 traceId 또는 service label로 바로 좁힐 수 있는지 확인한다.
- GC pause, heap used, CPU, thread, DB connection, request latency를 같은 시간축에서 비교한다.
- metrics label cardinality가 과도하게 커져 저장 비용을 키우지 않는지 확인한다.
- 알람이 “증상”만 말하는지, 다음 조사 링크(runbook/dashboard/log query)를 포함하는지 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| RED/USE 기반 대시보드 | 요청/자원 관점 기본 이상 감지 | 서비스별 커스터마이징 필요 |
| 공통 label 표준화 | metrics/logs/traces 연결 쉬움 | label cardinality 관리 필요 |
| traceId 로그 포함 | 단일 요청 원인 추적 가능 | context 전파 필요 |
| GC/DB/Thread 지표 동시 패널 | JVM 병목 가설 검증 쉬움 | 대시보드 관리 비용 |
| 알람별 runbook 연결 | 대응 속도 향상 | 문서 갱신 필요 |

---

## 트레이드오프

모든 데이터를 자세히 수집하면 원인 분석은 쉬워지지만 저장 비용, 개인정보 위험, 운영 복잡도가 커진다. 반대로 너무 적게 수집하면 장애가 난 뒤 내부 상태를 복원할 수 없다.

좋은 관측 설계는 모든 것을 저장하는 것이 아니라, 장애 가설을 검증할 수 있는 신호를 공통 축으로 연결하는 것이다.
