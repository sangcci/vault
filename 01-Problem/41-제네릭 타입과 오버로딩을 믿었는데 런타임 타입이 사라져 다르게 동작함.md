# Problem: 41-제네릭 타입과 오버로딩을 믿었는데 런타임 타입이 사라져 다르게 동작함

## 상황

제네릭 타입 `T`가 `Integer`라고 생각하고 오버로딩된 메서드가 선택될 것이라 기대했다. 하지만 실제로는 `Object` 버전이 호출되거나, `instanceof T`, `new T()` 같은 코드가 불가능하다.

```java
class Box<T> {
    T value;

    void print() {
        printer.print(value);
    }
}

void print(Integer v) { ... }
void print(Object v)  { ... }

new Box<Integer>().print();
// 기대: print(Integer)
// 실제: 컴파일 시 T가 Object로 소거되어 print(Object) 기준
```

---

## 관찰된 증거

- 런타임에 `List<String>`과 `List<Integer>`를 구분하려 한다.
- `T.class`, `new T()`, `instanceof T`가 불가능하다.
- 오버로딩 선택이 런타임 실제 객체 타입이 아니라 컴파일 타임 타입 기준으로 결정된다.
- override와 overload를 혼동한다.
- 필드 접근과 static method 호출이 다형적으로 동작한다고 기대한다.

---

## 의심 문제

가장 가능성 높은 문제는 **Java 제네릭의 타입 소거와 메서드 선택 시점을 혼동한 것**이다.

Java 제네릭은 컴파일 타임 타입 검사를 위한 장치이며, 런타임에는 타입 파라미터가 상한 또는 `Object`로 소거된다. 또한 overload는 컴파일 타임에, override는 런타임 실제 객체 타입에 따라 결정된다.

---

## 원인

```text
Type Erasure
  T unbounded → Object
  T extends Number → Number
  List<String>, List<Integer> → raw List 수준으로 동일

Overload
  - 컴파일 타임 타입으로 시그니처 선택
  - T가 Object로 보이면 print(Object) 선택

Override
  - 런타임 실제 객체의 구현 선택
  - virtual dispatch

Field/static method
  - 참조 타입 기준 정적 결정
```

---

## 확인 방법

- 문제 코드가 overload인지 override인지 먼저 구분한다.
- 제네릭 타입 정보가 런타임에 필요한지 확인한다.
- `Class<T>`, `TypeReference`, `ParameterizedType` 같은 타입 토큰이 필요한지 본다.
- API가 `List<T>` 내부 원소 타입을 런타임에 검사하려 하는지 확인한다.
- 필드 접근 대신 메서드 override를 사용해야 하는지 검토한다.

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| 타입 토큰 `Class<T>` 전달 | 런타임 타입 확인 가능 | API 인자 증가 |
| overload 대신 명시적 strategy/visitor | 선택 기준 명확 | 구조 복잡도 증가 |
| bounded type으로 상한 명확화 | 사용 가능 API 증가 | 런타임 구체 타입은 여전히 소거 |
| override 기반 다형성 사용 | 런타임 구현 선택 가능 | 상속/인터페이스 설계 필요 |
| 필드 다형성 기대 제거 | 오해 방지 | 캡슐화 필요 |

---

## 트레이드오프

Java 제네릭은 하위 호환성을 위해 런타임 타입 정보를 희생했다. 덕분에 별도 클래스 생성 없이 타입 안전성을 얻지만, 런타임 타입 분기와 생성에는 추가 타입 정보 전달이 필요하다.
