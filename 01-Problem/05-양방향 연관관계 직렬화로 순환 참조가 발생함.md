# Problem: 05-양방향 연관관계 직렬화로 순환 참조가 발생함

## 상황

JPA 엔티티가 양방향 연관관계를 가진 상태에서 Controller가 엔티티를 그대로 반환한다.

```java
@Entity
class Post {
    @OneToMany(mappedBy = "post")
    private List<Comment> comments;
}

@Entity
class Comment {
    @ManyToOne
    private Post post;
}

@GetMapping("/posts/{id}")
public Post getPost(@PathVariable Long id) {
    return postRepository.findById(id).orElseThrow();
}
```

JPA 내부에서는 정상적인 객체 그래프지만, JSON 직렬화 시점에는 `Post → Comment → Post → Comment ...`로 재귀가 이어질 수 있다.

---

## 관찰된 증거

- API 응답이 500으로 실패한다.
- `StackOverflowError` 또는 `HttpMessageNotWritableException`이 발생한다.
- 로그의 stack trace에서 Jackson serializer 호출이 반복된다.

```text
Post
 └─ comments[0]
      └─ post
           └─ comments[0]
                └─ post
                     └─ ...
```

---

## 의심 문제

가장 가능성 높은 문제는 **엔티티 양방향 참조를 API 응답 모델로 그대로 노출한 것**이다.

양방향 연관관계 자체가 항상 문제는 아니다. 문제는 영속성 모델의 탐색 구조와 외부 응답 JSON 구조를 분리하지 않은 데 있다.

---

## 원인

JPA 엔티티의 양방향 연관관계는 객체 탐색과 변경 편의를 위해 사용된다. 하지만 JSON은 트리 형태의 응답에 가깝고, 같은 객체를 다시 만났을 때 어디서 끊어야 하는지 자동으로 알기 어렵다.

```text
영속성 모델
Post ↔ Comment

API 응답 모델
PostResponse
 └─ comments[]
      └─ commentId, content
```

엔티티를 그대로 반환하면 내부 객체 그래프가 외부 API 계약이 된다. 이때 순환 참조뿐 아니라 Lazy Loading, 불필요한 필드 노출, 변경에 취약한 API 스키마 문제가 함께 생긴다.

---

## 확인 방법

- Controller 반환 타입이 Entity인지 확인한다.
- 응답 직렬화 대상 객체에 양방향 필드가 있는지 확인한다.
- stack trace에서 Jackson serializer가 같은 타입을 반복 처리하는지 확인한다.
- 응답 DTO 변환 후 문제가 사라지는지 비교한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| DTO 변환 | API 응답 모양을 명시하고 순환을 구조적으로 차단 | 매핑 코드 필요 |
| `@JsonIgnore` | 빠르게 한쪽 참조를 끊을 수 있음 | 엔티티가 API 직렬화 정책을 알게 됨 |
| `@JsonManagedReference` / `@JsonBackReference` | Jackson 기준으로 부모/자식 방향 지정 가능 | API별 응답 모양이 달라지면 관리 어려움 |
| 단방향 연관관계로 축소 | 객체 그래프 단순화 | 반대 방향 탐색이 필요한 조회에서 쿼리 작성 증가 |

---

## 트레이드오프

양방향 연관관계는 도메인 탐색과 변경 편의를 줄 수 있지만, API 응답 구조까지 양방향이어야 한다는 뜻은 아니다.

실무에서는 엔티티 관계는 내부 모델로 유지하고, 외부 응답은 DTO로 끊는 편이 안전하다. 이 방식은 매핑 비용을 추가하지만 순환 참조, 지연 로딩 노출, API 스키마 누수를 함께 줄인다.
