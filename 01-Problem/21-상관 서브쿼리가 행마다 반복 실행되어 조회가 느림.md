# Problem: 21-상관 서브쿼리가 행마다 반복 실행되어 조회가 느림

## 상황

서브쿼리로 조건을 깔끔하게 작성했는데, 데이터가 늘자 조회가 급격히 느려진다. `EXPLAIN ANALYZE`를 보면 `SubPlan`이 바깥 row 수만큼 반복 실행된다.

```sql
SELECT *
FROM orders o
WHERE o.total > (
    SELECT avg(o2.total)
    FROM orders o2
    WHERE o2.user_id = o.user_id
);
```

문장만 보면 안쪽 쿼리가 한 번 계산될 것 같지만, 바깥 row에 의존하는 순간 반복 실행될 수 있다.

---

## 관찰된 증거

```text
Seq Scan orders o
  Filter: total > (SubPlan 1)
  SubPlan 1
    -> Aggregate
       -> Scan orders o2
          Filter: o2.user_id = o.user_id
          loops = outer row 수
```

증상은 다음과 같다.

- `SubPlan`의 `loops`가 수천~수만 번이다.
- 내부 scan이 index를 못 타면 N+1과 비슷한 병목이 된다.
- `EXISTS`나 `IN`은 빠른데 scalar correlated subquery만 느리다.
- 같은 결과를 JOIN + GROUP BY로 바꾸면 빨라진다.

---

## 의심 문제

가장 가능성 높은 문제는 **서브쿼리가 join으로 decorrelation되지 못하고 outer row마다 실행되는 SubPlan으로 남은 것**이다.

서브쿼리는 항상 괄호 안을 먼저 실행하는 고정 절차가 아니다. planner는 가능하면 `Semi Join`, `Anti Join`, `InitPlan`, 일반 JOIN 등으로 바꾸지만, 모든 서브쿼리가 변환되는 것은 아니다.

---

## 원인

서브쿼리 실행 형태는 크게 나뉜다.

```text
InitPlan
  - outer row와 독립
  - query 시작 시 한 번 실행
  - 결과를 parameter로 재사용

SubPlan
  - outer row 값에 의존 가능
  - parent row 평가 중 호출
  - loops가 커질 수 있음

Semi / Anti Join
  - EXISTS / NOT EXISTS의 존재성 검사로 변환
  - inner row 전체를 붙이지 않음
```

문제가 되는 경우는 보통 이것이다.

```text
outer row 100,000개
  × correlated SubPlan 내부 scan 100,000회
  = 반복 실행 병목
```

---

## 확인 방법

- `EXPLAIN ANALYZE`에서 `SubPlan`, `InitPlan`, `Semi Join`, `Anti Join` 중 무엇으로 나왔는지 확인한다.
- `SubPlan` 내부 노드의 `loops`와 `actual time`을 곱해 총 비용을 본다.
- 내부 조건 컬럼에 인덱스가 있는지 확인한다.
- `EXISTS`, `JOIN`, `GROUP BY`로 재작성했을 때 plan이 바뀌는지 확인한다.
- `NOT IN`은 NULL semantics 때문에 `NOT EXISTS`와 결과가 달라질 수 있음을 확인한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| JOIN + GROUP BY로 재작성 | 반복 실행을 집합 연산으로 전환 | 중복 row와 집계 단위 주의 |
| EXISTS/NOT EXISTS 사용 | 존재성 검사 의도 명확 | NULL semantics 확인 필요 |
| 내부 조건 인덱스 추가 | SubPlan 반복 비용 감소 | outer row가 너무 많으면 한계 |
| 사전 집계 CTE/derived table | 평균/합계 재사용 가능 | materialization 비용 가능 |
| 통계 갱신 | planner 변환/비용 추정 개선 | 구조적 상관은 해결 안 될 수 있음 |

---

## 트레이드오프

서브쿼리는 표현력이 좋지만, 실행계획에서는 한 번 계산되는 값인지, row마다 반복되는 작업인지가 핵심이다. SQL을 읽을 때의 논리적 포함 관계보다 `loops`와 plan node가 실제 비용을 말해준다.
