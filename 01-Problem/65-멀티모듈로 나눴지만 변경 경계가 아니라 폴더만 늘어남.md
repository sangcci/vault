# Problem: 65-멀티모듈로 나눴지만 변경 경계가 아니라 폴더만 늘어남

## 상황

프로젝트를 깔끔하게 만들기 위해 api, domain, infra, common 같은 멀티모듈로 나눴다. 하지만 실제 의존성 규칙은 없고, 도메인 모듈이 infra 구현체를 참조하거나 common 모듈이 모든 것을 알고 있어 구조가 더 복잡해진다.

```text
나쁜 구조
api -> domain -> infra
       ^       ↘
       └ common ← everything

좋은 질문
이 모듈은 무엇과 독립적으로 변경/배포/테스트되어야 하는가?
```

---

## 관찰된 증거

- 모듈은 많지만 순환 의존을 우회하기 위해 common이 비대해진다.
- 작은 변경에도 여러 모듈의 Gradle 설정과 테스트 wiring을 만진다.
- 팀원이 usecase 흐름보다 모듈 구조를 먼저 이해해야 한다.
- API 서버와 batch의 실행 특성이 다른데도 같은 모듈에 묶여 있다.
- 반대로 단순 CRUD인데 멀티모듈 비용만 생긴다.

---

## 원인

모듈은 폴더 정리가 아니라 변경 경계와 의존성 방향을 강제하는 장치다. 변경 이유, 실행 단위, 기술 교체 지점이 분명하지 않은 상태에서 나누면 구조가 아니라 설정 비용이 먼저 늘어난다.

---

## 해결 방향

- 단순 CRUD는 layered architecture로 시작한다.
- Service가 비대해지면 먼저 usecase와 도메인 책임을 정리한다.
- DB/Redis/외부 API 같은 기술 교체 지점이 반복되면 adapter로 분리한다.
- API/batch/scheduler의 배포·자원·장애 격리 기준이 다르면 실행 모듈을 분리한다.
- 모듈 도입 전 의존성 방향과 금지 규칙을 문서화한다.
