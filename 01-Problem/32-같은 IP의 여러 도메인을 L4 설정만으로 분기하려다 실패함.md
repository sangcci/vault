# Problem: 32-같은 IP의 여러 도메인을 L4 설정만으로 분기하려다 실패함

## 상황

하나의 서버 IP에 여러 도메인을 연결했다. `a.example.com`은 서비스 A로, `b.example.com`은 서비스 B로 보내고 싶어서 iptables/NAT/L4 설정만으로 분기하려 한다.

```text
a.example.com → 203.0.113.10
b.example.com → 203.0.113.10

요구사항:
  a.example.com → container A
  b.example.com → container B
```

하지만 L4 장비나 iptables는 도메인별로 요청을 나누지 못한다.

---

## 관찰된 증거

- DNS는 두 도메인을 같은 IP로 잘 해석한다.
- TCP 연결 단계에서는 목적지 IP:Port만 보인다.
- iptables DNAT은 `203.0.113.10:443`까지는 알지만 `Host: a.example.com`을 모른다.
- Nginx/ALB/Cloudflare 같은 L7 라우터를 두면 Host 기준 분기가 된다.
- HTTP/1.1 요청에서 Host 헤더가 빠지면 가상 호스팅이 불가능하다.

---

## 의심 문제

가장 가능성 높은 문제는 **계층별로 볼 수 있는 정보가 다른데 L3/L4 도구로 L7 정보를 읽으려 한 것**이다.

IP/Port 기반 라우팅과 Host/Path/Header 기반 라우팅은 대체 관계가 아니라 계층이 다르다.

---

## 원인

```text
L3/L4가 보는 것
  - source IP
  - destination IP
  - port
  - protocol TCP/UDP

L7이 보는 것
  - Host header
  - path
  - method
  - cookie/header
  - HTTP body 일부
```

가상 호스팅은 HTTP 요청 안의 Host header가 있어야 가능하다.

```http
GET / HTTP/1.1
Host: a.example.com
```

따라서 같은 IP:Port로 들어온 두 도메인을 나누려면 HTTP를 이해하는 L7 proxy가 필요하다.

---

## 확인 방법

- 분기 기준이 IP/Port인지, Host/Path/Header인지 먼저 적는다.
- iptables/NAT으로 처리하려는 조건에 HTTP 정보가 들어 있는지 확인한다.
- TLS 환경이면 SNI/Host 처리 위치를 확인한다.
- Nginx `server_name`, ALB host-based rule, Cloudflare routing rule을 확인한다.
- L4 LB 뒤에 L7 reverse proxy가 필요한 구조인지 본다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| Nginx/HAProxy L7 라우팅 | Host/Path 기준 분기 가능 | proxy 운영 필요 |
| AWS ALB/Cloudflare | 관리형 L7 라우팅 | 비용/벤더 정책 |
| 도메인별 IP 분리 | L4만으로 분기 가능 | IP/인프라 비용 |
| 포트별 서비스 분리 | 단순 | 사용자 URL/보안 정책 불편 |
| L4 + L7 역할 분담 | 계층별 책임 명확 | 구성 복잡도 증가 |

---

## 트레이드오프

L4는 빠르고 단순하지만 애플리케이션 의미를 모른다. L7은 Host/Path/Header를 기준으로 정교하게 라우팅할 수 있지만 HTTP 해석과 proxy 운영 비용이 생긴다. 라우팅 문제는 먼저 “분기 기준이 어느 계층의 정보인가”를 정해야 한다.
