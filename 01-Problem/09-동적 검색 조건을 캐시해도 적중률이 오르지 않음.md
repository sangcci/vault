# Problem: 09-동적 검색 조건을 캐시해도 적중률이 오르지 않음

## 상황

목록 검색 API가 느려서 `@Cacheable`을 붙였다.

```java
@Cacheable(cacheNames = "products")
public Page<ProductResponse> search(String keyword, String sort, int page) {
    return productRepository.search(keyword, sort, page);
}
```

하지만 캐시 hit rate가 거의 오르지 않고, 힙 메모리 사용량만 증가한다.

---

## 관찰된 증거

```text
keyword × sort × page

"spring" × "latest" × 1  -> key A
"spring" × "latest" × 2  -> key B
"spring" × "popular" × 1 -> key C
"jpa"    × "latest" × 1  -> key D
...

대부분의 key가 한 번만 쓰이고 사라짐
```

운영 증상은 다음과 같다.

- cache entry 수는 계속 증가하지만 hit rate는 낮다.
- eviction이 빈번하고 GC 부담이 커진다.
- 캐시를 적용했는데도 DB 조회 수가 줄지 않는다.
- 검색 파라미터 조합이 늘수록 캐시 효율이 더 떨어진다.

---

## 의심 문제

가장 가능성 높은 문제는 **캐시 키 공간 폭발**이다.

캐시는 “반복 접근되는 값”을 저장할 때 효과가 있다. 요청마다 key가 달라지면 캐시는 빠른 저장소가 아니라 메모리를 쓰는 통과 지점이 된다.

---

## 원인

동적 검색 조건을 그대로 캐시 key로 쓰면 가능한 key 수가 런타임에 계속 늘어난다.

```text
키워드 n개 × 정렬 m개 × 페이지 k개 × 필터 p개
  ↓
캐시 key 공간 = n × m × k × p
  ↓
반복 접근 확률 감소
  ↓
hit rate 하락 + eviction 증가
```

핵심은 데이터가 자주 조회되는지가 아니라 **같은 key로 다시 조회되는지**다. 인기 데이터라도 검색 조건 조합이 매번 다르면 캐시 관점에서는 다른 데이터다.

---

## 확인 방법

- cache key cardinality를 측정한다.
- key별 접근 횟수 분포를 본다. 1회 접근 key가 대부분이면 캐시 부적합이다.
- hit rate뿐 아니라 entry count, eviction count, 평균 value size를 함께 본다.
- 정렬, 페이지, 필터 중 key에서 제외하거나 정규화할 수 있는 요소를 찾는다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| 정형 쿼리만 캐시 | hit rate 예측 가능 | 캐시 대상 범위 제한 |
| key 정규화 | 중복 key 감소 | 애플리케이션에서 후처리 필요 |
| 상위 N개/첫 페이지 캐시 | 트래픽 집중 구간 최적화 | 긴 꼬리 검색은 DB/검색 엔진 사용 |
| Redis 등 글로벌 캐시 | 인스턴스 간 중복 캐시 감소 | 네트워크 비용과 운영 비용 증가 |
| 검색 엔진 위임 | 동적 검색에 적합 | 색인 지연과 운영 복잡도 증가 |

---

## 트레이드오프

캐시는 모든 느린 쿼리의 해결책이 아니다. key 공간이 무한히 커지는 조회는 캐시보다 쿼리 최적화, 검색 엔진, 집계 테이블이 더 적합할 수 있다.

캐시를 적용할 때는 “이 값이 비싼가”보다 “이 key가 반복되는가”를 먼저 확인해야 한다.
