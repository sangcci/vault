# Problem: 06-인덱스를 추가했는데도 조회 쿼리가 느림

## 상황

조회 조건에 맞춰 인덱스를 추가했는데도 API 응답 시간이 줄지 않는다.

```sql
CREATE INDEX idx_orders_status ON orders(status);

EXPLAIN ANALYZE
SELECT *
FROM orders
WHERE status = 'PAID';
```

개발자는 “인덱스를 탔으니 빨라야 한다”고 기대하지만, 실제 실행 계획은 `Seq Scan`이거나 `Index Scan`이어도 대부분의 row를 읽고 있다.

---

## 관찰된 증거

```text
Seq Scan on orders
  Filter: (status = 'PAID')
  Rows Removed by Filter: 30000
  Buffers: shared hit=1200 read=80
```

또는 다음처럼 인덱스를 사용하지만 느릴 수 있다.

```text
Index Scan using idx_orders_status on orders
  Index Cond: (status = 'PAID')
  Filter: (created_at >= now() - interval '7 days')
  Rows Removed by Filter: 180000
```

관찰 포인트는 다음이다.

- `Index Cond`가 후보 row를 충분히 줄였는가?
- `Filter`에서 버린 row가 지나치게 많지 않은가?
- `actual rows`가 planner의 예상 `rows`와 크게 다르지 않은가?
- `Buffers: shared read`가 커서 디스크에서 page를 많이 읽고 있지 않은가?

---

## 의심 문제

가장 가능성 높은 문제는 **인덱스 존재 여부가 아니라 선택도와 접근 경로가 쿼리 조건에 맞지 않는 것**이다.

인덱스는 “무조건 빠른 경로”가 아니라 “후보 row를 충분히 줄일 수 있을 때 빠른 경로”다.

---

## 원인

DB는 SQL의 논리 조건을 물리 접근 계획으로 바꾼다. 이때 비용은 단순히 인덱스 유무가 아니라 다음 요소로 결정된다.

```text
WHERE 조건
  ↓
선택도 추정
  ↓
접근 경로 선택
  ├─ Seq Scan
  ├─ Index Scan
  └─ Bitmap Heap Scan
  ↓
heap page 접근 + tuple visibility + Filter 평가
```

매칭 row가 많으면 인덱스로 TID를 찾더라도 heap page를 랜덤하게 많이 방문해야 한다. 이 경우 차라리 테이블을 순차로 읽는 `Seq Scan`이 더 싸다.

또 복합 조건 중 일부만 `Index Cond`로 내려가고 나머지가 `Filter`로 남으면, 인덱스를 탔는데도 heap tuple을 많이 읽은 뒤 버리게 된다.

---

## 확인 방법

- `EXPLAIN (ANALYZE, BUFFERS)`로 실제 실행 시간, row 수, buffer 접근을 확인한다.
- `Index Cond`와 `Filter`를 분리해서 읽는다.
- `Rows Removed by Filter`가 크면 복합 인덱스 순서나 조건식을 재검토한다.
- `actual rows`와 예상 `rows` 차이가 크면 통계 정보와 데이터 분포를 확인한다.
- 매칭 비율이 높다면 인덱스 추가보다 쿼리 조건, 파티셔닝, partial index, covering index를 검토한다.

---

## 해결책 후보

| 해결책 | 장점 | 비용/위험 |
|---|---|---|
| 복합 인덱스 조정 | `Filter`를 `Index Cond`로 더 많이 내릴 수 있음 | 조건 순서와 카디널리티 이해 필요 |
| Partial Index | 자주 쓰는 조건 subset만 작게 유지 | 조건이 바뀌면 활용도 감소 |
| Covering Index | heap 접근을 줄일 수 있음 | 인덱스 크기와 쓰기 비용 증가 |
| 쿼리 조건 재설계 | 선택도를 높여 scan 범위 축소 | API 요구사항 변경 필요할 수 있음 |
| 통계 갱신 | planner 예측 개선 | 데이터 분포가 계속 변하면 반복 관리 필요 |

---

## 트레이드오프

인덱스를 늘리면 읽기 경로는 늘어나지만 쓰기 비용, 저장 공간, planner 선택지는 함께 증가한다.

따라서 느린 쿼리를 볼 때는 “인덱스가 있는가”보다 “이 쿼리가 실제로 몇 개의 heap page와 tuple을 읽었는가”를 먼저 봐야 한다.
