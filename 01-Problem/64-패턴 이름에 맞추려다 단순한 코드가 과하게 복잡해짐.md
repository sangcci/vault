# Problem: 64-패턴 이름에 맞추려다 단순한 코드가 과하게 복잡해짐

## 상황

간단한 조건 분기나 객체 생성을 처리하면 되는 상황에서 Strategy, Factory, Visitor 같은 패턴 이름을 먼저 정하고 설계를 시작한다. 결과적으로 클래스와 인터페이스는 늘었지만, 실제 변경 가능성은 낮고 코드 읽는 비용만 커진다.

```text
문제: 결제 수단별 수수료 계산 2개
나쁜 흐름: "Strategy 패턴 써야겠다"
결과: Interface + Factory + Context + Impl 여러 개

좋은 흐름: 조건이 늘고 변경 이유가 분리될 때 구조를 분리
```

---

## 관찰된 증거

- 파일 수는 많지만 변경 이유가 분명하지 않다.
- 팀원이 패턴 이름은 아는데 실제 문제를 설명하지 못한다.
- 단순 CRUD에도 추상 계층이 반복해서 생긴다.
- 테스트가 쉬워진 것도 아니고 교체 가능성이 실제로 존재하지도 않는다.
- 패턴 적용 자체가 설계 목표가 된다.

---

## 원인

디자인 패턴은 반복되는 문제와 해결 구조에 붙인 어휘다. 패턴은 코드 읽기와 소통을 돕지만, 문제보다 먼저 오면 오버엔지니어링이 된다.

---

## 해결 방향

- 패턴 이름보다 해결하려는 변경 가능성과 중복을 먼저 적는다.
- 숨길 복잡성이 없으면 추상 계층을 추가하지 않는다.
- 패턴은 설계 시작점이 아니라 설명 어휘로 쓴다.
- 실무에서는 작은 리팩터링으로 구조가 드러난 뒤 이름을 붙인다.
- 면접/문서에서는 “무슨 패턴인가”보다 “무슨 문제를 줄였는가”를 설명한다.
