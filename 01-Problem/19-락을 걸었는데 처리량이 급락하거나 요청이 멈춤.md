# Problem: 19-락을 걸었는데 처리량이 급락하거나 요청이 멈춤

## 상황

공유 상태를 보호하기 위해 `synchronized`나 `ReentrantLock`을 추가했다. 데이터 꼬임은 줄었지만, 트래픽이 올라가면 응답 시간이 급증하거나 일부 요청이 영원히 끝나지 않는다.

```java
private final Object lockA = new Object();
private final Object lockB = new Object();

public void transferAtoB() {
    synchronized (lockA) {
        synchronized (lockB) {
            move();
        }
    }
}

public void transferBtoA() {
    synchronized (lockB) {
        synchronized (lockA) {
            moveBack();
        }
    }
}
```

정확성을 위해 락을 걸었는데 시스템의 활동성이 깨진다.

---

## 관찰된 증거

```text
Lock Contention
Thread A: lock 획득 → 긴 작업 수행
Thread B/C/D: lock 대기
결과: CPU는 낮은데 응답 시간 증가

Deadlock
Thread A: lockA 보유, lockB 대기
Thread B: lockB 보유, lockA 대기
결과: 둘 다 진행 불가
```

증상은 다음과 같다.

- CPU 사용률은 낮은데 처리량이 떨어진다.
- thread dump에서 `BLOCKED`, `WAITING`, `parking to wait for`가 많이 보인다.
- 요청 stack trace 대부분이 lock 획득 지점에 머문다.
- 특정 순서의 요청이 들어오면 재시작 전까지 회복되지 않는다.

---

## 의심 문제

가장 가능성 높은 문제는 **임계 구역을 너무 크게 잡았거나, 여러 락의 획득 순서가 일관되지 않은 것**이다.

락은 데이터 안전성을 높이지만, 동시에 실행 흐름을 직렬화한다. 락이 보호하는 구간이 길수록 대기열이 길어지고, 여러 락이 얽히면 교착 상태가 된다.

---

## 원인

락 문제는 크게 두 종류로 나뉜다.

```text
Safety 문제 해결
  → 한 번에 하나만 들어오게 함
  → race condition 감소

Liveness 문제 발생
  → 너무 오래 기다림
  → 서로 기다림
  → 아무도 진행하지 못함
```

교착 상태는 보통 다음 네 조건이 동시에 성립할 때 발생한다.

```text
1. 상호 배제: 자원을 동시에 쓸 수 없음
2. 점유와 대기: 하나를 가진 채 다른 자원을 기다림
3. 비선점: 가진 자원을 강제로 빼앗을 수 없음
4. 환형 대기: A는 B를, B는 A를 기다림
```

---

## 확인 방법

- thread dump에서 같은 monitor 또는 `ReentrantLock` 대기 스레드가 많은지 확인한다.
- lock 내부에서 DB, 외부 API, 파일 I/O, sleep 같은 느린 작업을 하는지 본다.
- 여러 lock을 잡는 코드의 획득 순서가 전역적으로 동일한지 확인한다.
- `tryLock(timeout)`으로 바꾸면 요청이 영원히 멈추지 않는지 확인한다.
- APM에서 lock wait 시간이 전체 latency의 대부분인지 본다.

## 해결책 후보

| 해결책 | 장점 | 비용/주의 |
|---|---|---|
| 임계 구역 축소 | 경합 시간 감소 | 보호해야 할 불변식 재검토 필요 |
| 락 획득 순서 고정 | deadlock 예방 | 모든 코드 경로 규칙 필요 |
| `tryLock(timeout)` | 무한 대기 방지 | 실패 처리/보상 로직 필요 |
| 락 분할/샤딩 | 경합 분산 | 복잡도 증가 |
| 불변/복사 후 교체 | 공유 변경 최소화 | 메모리 비용 증가 |
| 큐/단일 writer | 순서 명확 | 지연과 backpressure 설계 필요 |

---

## 트레이드오프

락은 공유 상태를 보호하는 가장 직관적인 도구지만, 보호 범위가 곧 병목 범위가 된다. 락을 추가했다면 “데이터가 맞는가”뿐 아니라 “기다리는 동안 시스템이 계속 진행하는가”도 함께 검증해야 한다.
