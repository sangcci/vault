# Principle: 전송 배치 크기와 메모리 압력

**핵심 질문**: DB가 row를 빨리 찾아도 애플리케이션은 왜 대량 결과 처리에서 느려지거나 메모리가 터지는가?

## 한 문장 정의

전송 배치 크기와 메모리 압력은 생산자가 만든 데이터를 소비자에게 한 번에 얼마나 옮길지에 따라 네트워크 왕복, 버퍼 메모리, 처리 지연이 서로 교환된다는 원리.

---

## 해결하는 문제

- 대량 조회 API가 DB 실행보다 애플리케이션 전송 구간에서 느린 문제
- JDBC ResultSet이 전체 결과를 한 번에 가져와 heap을 압박하는 문제
- fetch size를 키우면 항상 빠르다고 오해하는 문제
- cursor streaming이 장기 트랜잭션과 충돌할 수 있다는 점을 놓치는 문제

---

## 판단 기준

```text
작은 fetch size
  → round trip 많음
  → 메모리 작음
  → latency 증가 가능

큰 fetch size / 전체 fetch
  → round trip 적음
  → 메모리 큼
  → GC/OOM 위험

cursor streaming
  → 메모리 안정
  → transaction 오래 열림
  → MVCC cleanup 지연 가능
```

---

## 진단 포인트

- DB execution time과 ResultSet processing time을 분리한다.
- fetch size 적용 조건이 드라이버별로 맞는지 확인한다.
- PostgreSQL JDBC는 autocommit=false 조건을 확인한다.
- API 응답이면 pagination이 맞는지, batch/export면 streaming이 맞는지 구분한다.
- 긴 streaming 조회가 MVCC snapshot을 오래 붙잡는지 확인한다.

---

## 트레이드오프

전송 배치 크기는 처리량과 메모리의 교환이다. 크게 가져오면 왕복은 줄지만 소비자가 감당해야 하는 버퍼가 커지고, 작게 가져오면 메모리는 안정되지만 네트워크 왕복과 프로토콜 비용이 늘어난다.
