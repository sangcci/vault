# Principle: 격리 강도와 자원 경계

**핵심 질문**: 어떤 워크로드는 컨테이너로 충분하고, 어떤 워크로드는 VM이나 별도 인프라 경계가 필요한가?

## 한 문장 정의

격리는 “보이지 않게 하는 경계”와 “못 쓰게 제한하는 경계”의 조합이며, 워크로드의 보안·영속성·자원 민감도에 따라 필요한 강도가 달라진다.

---

## 해결하는 문제

- Docker와 VM 격리 수준을 구분하지 못해 워크로드 배치가 불안정한 문제
- 같은 host의 다른 컨테이너 때문에 latency가 흔들리는 Noisy Neighbor 문제
- stateful DB를 컨테이너 생명주기와 같은 방식으로 다뤄 복구 위험이 커지는 문제
- 격리 수준을 높일수록 비용이 왜 증가하는지 설명하지 못하는 문제

---

## 깨지는 상황

```text
컨테이너 = VM과 같은 격리라고 가정
  ↓
DB / batch / WAS를 같은 host에 배치
  ↓
공유 kernel / shared I/O / shared memory pressure
  ↓
한 워크로드의 자원 폭주가 다른 워크로드로 전파
```

컨테이너는 독립된 실행 환경처럼 보이지만, 커널과 물리 자원은 공유한다. 따라서 격리는 “있다/없다”가 아니라 “어느 계층까지 끊었는가”로 봐야 한다.

---

## 판단 기준

- stateless 애플리케이션은 Docker로 배포 단위를 관리하기 좋다.
- 보안 민감도나 tenant 간 불신이 크면 VM, MicroVM, gVisor 같은 더 강한 경계를 검토한다.
- DB, queue, persistent cache처럼 영속성과 I/O 안정성이 중요한 워크로드는 전용 VM이나 managed service를 우선 검토한다.
- CPU/memory/disk I/O limit 없이 컨테이너를 섞으면 Noisy Neighbor를 피하기 어렵다.
- 장애가 전파되어도 되는 범위를 먼저 정하고, 그 범위에 맞춰 VM/컨테이너/프로세스 경계를 선택한다.

---

## 트레이드오프

| 경계 | 얻는 것 | 잃는 것 |
|---|---|---|
| 프로세스 | 가장 가벼움 | 환경/자원 격리 약함 |
| 컨테이너 | 빠른 배포, 의존성 격리, resource limit | kernel 공유, 보안 경계 약함 |
| VM | 독립 kernel, 강한 장애/보안 경계 | 부팅/운영/비용 증가 |
| Managed Service | 운영 책임 감소, 안정성 | 비용, 커스터마이징 제한 |
| MicroVM/gVisor | 컨테이너보다 강한 tenant 격리 | 복잡도와 오버헤드 |
