# Principle: 의존성 방향과 기술 격리

**핵심 질문**: 비즈니스 코드는 외부 기술을 어디까지 알아야 하는가?

## 한 문장 정의

의존성 방향과 기술 격리는 core가 제품 규칙의 언어로 port를 정의하고, 외부 기술은 adapter가 그 port를 구현하게 하여 기술 변경이 비즈니스 규칙으로 전파되지 않게 하는 원리.

---

## 해결하는 문제

- 도메인 코드에 DB, Redis, FCM, OAuth2 같은 기술 이름이 새어 나오는 문제
- Entity가 Repository나 Spring Context를 직접 아는 문제
- 외부 SDK 없이 core 규칙 테스트가 어려운 문제
- 기술 교체가 비즈니스 로직 변경으로 번지는 문제

---

## 판단 기준

```text
기술이 바뀌면 바뀐다
  → adapter / infrastructure

제품 정책이 바뀌면 바뀐다
  → application / domain

core가 외부 기능을 필요로 한다
  → port interface로 요구사항 표현

외부 기술로 실제 수행한다
  → adapter implementation
```

---

## 진단 포인트

- core 패키지에 vendor/protocol/SDK 이름이 있는가?
- port 이름이 `FcmSender` 같은 기술 이름인가, `NotificationSender` 같은 제품 언어인가?
- Repository가 도메인 객체 접근 컬렉션처럼 보이는가, ORM 세부 기능 노출 창구인가?
- 테스트에서 실제 DB/Redis/FCM 없이는 규칙 검증이 불가능한가?

---

## 트레이드오프

Port/Adapter는 변경과 테스트에는 유리하지만 interface와 mapping 비용이 생긴다. 모든 기술 의존을 무조건 제거하기보다, core 규칙이 기술 교체 때문에 흔들리는 지점을 우선 격리한다.
