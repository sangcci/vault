# Principle: 병렬성과 하드웨어 한계

**핵심 질문**: 동시에 다루는 작업 수와 실제 동시에 실행되는 작업 수는 왜 다른가?

## 한 문장 정의

병렬성과 하드웨어 한계는 동시성은 여러 작업을 겹쳐 다루는 구조이고, 병렬성은 하드웨어 실행 슬롯 수만큼 실제로 동시에 실행되는 물리적 성질이라는 원리.

---

## 해결하는 문제

- 스레드 수를 늘리면 그만큼 동시에 실행된다고 오해하는 문제
- 이벤트 루프, 멀티스레드, 멀티프로세스를 모두 같은 병렬 처리로 보는 문제
- CPU-bound 작업에서 core 수 이상의 worker를 만들어 성능이 떨어지는 문제
- I/O 대기 숨기기와 실제 CPU 병렬 실행을 구분하지 못하는 문제

---

## 판단 기준

```text
동시성 Concurrency
  - 여러 작업을 겹쳐 다룸
  - 대기 시간을 다른 작업으로 채움
  - 단일 core에서도 가능

병렬성 Parallelism
  - 여러 작업이 실제 같은 시점에 실행됨
  - hardware thread/logical processor 수에 제한됨
  - CPU-bound 성능 향상과 직접 연결
```

---

## 진단 포인트

- 작업이 CPU-bound인지 I/O-bound인지 구분한다.
- logical CPU 수와 runnable worker 수를 비교한다.
- 대기 시간이 많은 작업은 동시성 확장이 유리할 수 있다.
- 순수 CPU 연산은 하드웨어 thread 수를 넘기면 context switch와 cache 경합이 늘 수 있다.
- 병렬화할 수 없는 순차 구간이 전체 성능 향상을 제한하는지 확인한다.

---

## 트레이드오프

병렬성을 늘리면 CPU 연산 처리량은 늘 수 있지만, 분할·병합·동기화 비용이 생긴다. 동시성을 늘리면 대기 시간을 활용할 수 있지만, 공유 상태와 스케줄링 비용이 늘어난다.
