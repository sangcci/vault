# Principle: 원자적 상태 전이

**핵심 질문**: 상태를 읽고 판단하고 바꾸는 과정을 하나의 쪼갤 수 없는 전이로 만들 수 있는가?

## 한 문장 정의

원자적 상태 전이는 **현재 상태 확인, 업무 조건 검증, 상태 변경을 하나의 분리 불가능한 연산으로 묶어 중간에 다른 요청이 끼어들어도 오래된 판단으로 상태를 덮어쓰지 못하게 하는 원리**다.

---

## 해결하는 문제

이 본질은 여러 사람이 같은 상태를 동시에 바꾸는 문제에서 반복된다.

```text
- 재고 차감
- 예약 잔여 좌석 감소
- 신청 인원 증가
- 쿠폰 발급 수량 증가
- 포인트 잔액 차감
- 주문 상태 전이
```

깨지는 구조는 대부분 같다.

```text
READ current state
  → application memory에서 판단
  → WRITE calculated value
```

동시 요청이 들어오면 여러 요청이 같은 예전 상태를 읽고 각자 계산한 값을 저장한다.

```text
count = 10

T1: read 10 → write 11
T2: read 10 → write 11
T3: read 10 → write 11

기대: 13
실제: 11
```

---

## 깨지는 상황

`@Transactional`만으로 원자적 상태 전이가 자동 보장된다고 착각할 때 깨진다.

```text
트랜잭션이 보장하는 것:
  commit / rollback 단위

트랜잭션만으로 부족한 것:
  내가 읽은 값이 쓰기 시점에도 유효한지
  다른 요청이 중간에 같은 값을 바꿨는지
  검증과 변경이 하나의 상태 전이인지
```

위험한 코드 구조:

```java
Stock stock = stockRepository.findById(id).orElseThrow();
if (stock.getQuantity() < orderQuantity) {
    throw new OutOfStockException();
}
stock.decrease(orderQuantity);
```

위험한 SQL 구조:

```sql
SELECT quantity FROM stock WHERE id = 1;
-- application calculates quantity = 9
UPDATE stock SET quantity = 9 WHERE id = 1;
```

안전한 방향은 검증과 변경을 DB의 한 연산으로 밀어 넣는 것이다.

```sql
UPDATE stock
SET quantity = quantity - :amount
WHERE id = :id
  AND quantity >= :amount;
```

## 판단 기준

먼저 상태 변경이 단순한지 확인한다.

```text
변경이 단일 row의 단순 증감/차감인가?
  ├─ YES → Atomic UPDATE 우선
  │        UPDATE ... SET count = count + :delta
  │        WHERE count + :delta <= max
  │
  └─ NO  → 읽은 값 기반으로 복잡한 판단을 하는가?
           ├─ 충돌 낮고 재시도 가능 → Optimistic Lock
           ├─ 충돌 높고 직렬화 필요 → Pessimistic Lock
           └─ 여러 row/table invariant → 격리 수준/제약/상태 모델 재설계
```

Atomic UPDATE가 잘 맞는 조건:

```text
- 상태 변경이 하나의 SQL로 표현 가능하다.
- 성공/실패를 rowCount로 판단해도 충분하다.
- 실패 이유를 세밀하게 구분하지 않아도 된다.
- UI의 stale read를 허용하고 최종 검증을 쓰기 시점에 할 수 있다.
```

Atomic UPDATE가 부족한 조건:

```text
- 현재 값을 읽어 가격, 등급, 보상 같은 별도 결정을 해야 한다.
- 여러 row를 함께 보고 invariant를 만족시켜야 한다.
- 특정 좌석 번호처럼 개별 자원을 배정해야 한다.
- 실패 시 사용자에게 세밀한 원인 설명이 필요하다.
```

## 트레이드오프

```text
Atomic UPDATE
  얻는 것: 단순함, 성능, Lost Update 방지
  잃는 것: 복잡한 업무 판단 표현력, 실패 원인 세분화

Optimistic Lock
  얻는 것: 기존 엔티티 모델 유지, 충돌 감지
  잃는 것: 재시도 로직, 충돌 많은 상황의 실패율

Pessimistic Lock
  얻는 것: 읽은 값 기반 판단 보호
  잃는 것: lock 대기, deadlock, connection 점유
```

중요한 기준:

```text
상태 전이는 가능한 한 데이터가 있는 곳에서 원자적으로 처리한다.
애플리케이션 메모리에서 계산한 값을 나중에 쓰는 구조는 동시성 창을 만든다.
```
