# Principle: 유스케이스 흐름과 도메인 책임 분리

**핵심 질문**: Service는 어디까지 알고, Domain은 무엇을 책임져야 하는가?

## 한 문장 정의

유스케이스 흐름과 도메인 책임 분리는 요청 하나의 실행 순서와 트랜잭션 경계는 Application Service가 조립하고, 업무 규칙과 상태 불변식은 Domain/Policy가 판단하게 나누는 원리.

---

## 해결하는 문제

- Service 코드가 조회, 저장, 예외 처리, 도메인 규칙으로 비대해지는 문제
- Entity가 데이터 박스가 되고 모든 규칙이 service 조건문에 흩어지는 문제
- Domain Service/Policy와 Application Service의 차이를 구분하지 못하는 문제
- Reader/Writer/Joiner 같은 implementation actor를 언제 둘지 판단하는 문제

---

## 판단 기준

```text
Application Service
  - usecase 순서
  - transaction boundary
  - event 발행 순서

Implementation Actor
  - repository 조회
  - not found 처리
  - 저장 위임
  - 외부 port 호출 준비

Domain / Policy
  - 업무 규칙
  - 불변식
  - 상태 변경의 정당성
```

---

## 진단 포인트

- “이 조건은 업무적으로 가능한가?” → Domain/Policy 후보
- “이 객체를 어디서 찾아오고 없으면 어떻게 할까?” → Implementation 후보
- “이 usecase는 어떤 순서로 실행되고 어디까지 transaction인가?” → Application 후보
- “기술 실패나 외부 호출 방식인가?” → Adapter/Infrastructure 후보

---

## 트레이드오프

Transaction Script는 단순 usecase에서 빠르고 명확하다. 하지만 규칙과 변경 이유가 늘어나면 service가 비대해진다. 계층 분리는 복잡도를 없애는 것이 아니라 변경 이유별로 복잡도를 배치하는 선택이다.
