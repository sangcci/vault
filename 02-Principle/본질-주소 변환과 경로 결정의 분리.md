# Principle: 주소 변환과 경로 결정의 분리

**핵심 질문**: DNAT을 설정했는데도 왜 패킷이 목적지에 도달하지 않을 수 있는가?

## 한 문장 정의

주소 변환은 패킷 헤더의 출발지·목적지를 바꾸는 단계이고, 경로 결정은 변경된 주소를 기준으로 나갈 인터페이스를 고르는 별도 단계다.

---

## 해결하는 문제

- DNAT 설정 후에도 VM 서비스에 외부 접속이 되지 않는 문제
- NAT 테이블과 라우팅 테이블을 같은 역할로 오해하는 문제
- `ufw allow`와 `ufw route allow` 차이를 놓치는 문제
- 프라이빗 서브넷 WAS가 공인 IP 없이 외부 API를 호출하는 구조를 설명하지 못하는 문제

---

## 깨지는 상황

```text
DNAT만 설정
  ↓
목적지 주소는 VM IP로 바뀜
  ↓
Routing/FORWARD 허용 누락
  ↓
패킷이 Host를 경유하지 못하고 DROP
```

또는 다음처럼 방향을 혼동한다.

```text
SNAT/NAT Gateway
  내부 → 외부 아웃바운드 가능
  외부 → 내부 인바운드 시작 불가
```

---

## 판단 기준

- DNAT은 “외부 주소를 내부 주소로 바꾸는 것”이지 통과 허용이 아니다.
- 라우팅 테이블은 “어느 인터페이스로 내보낼지”를 결정한다.
- Host 자신이 목적지면 INPUT 체인, Host를 경유해 VM/컨테이너로 가면 FORWARD 체인을 본다.
- 프라이빗 서버가 외부로 나가기만 하면 SNAT/NAT Gateway를 사용한다.
- 외부에서 내부로 들어와야 하면 DNAT, Load Balancer, Tunnel, Public IP 중 어떤 노출 방식을 쓸지 정한다.

```text
외부 → 내부 포워딩
PREROUTING(DNAT) → Routing → FORWARD → POSTROUTING(optional SNAT)

내부 → 외부 아웃바운드
Routing → POSTROUTING(SNAT/MASQUERADE) → Internet
```

---

## 트레이드오프

| 방식 | 얻는 것 | 잃는 것 |
|---|---|---|
| DNAT 포트포워딩 | 내부 VM 서비스 외부 노출 | FORWARD/firewall 관리 필요 |
| SNAT/MASQUERADE | 사설 IP의 외부 통신 | 내부 실제 IP 투명성 감소 |
| NAT Gateway | 프라이빗 서브넷 아웃바운드 | 비용, 인바운드 불가 |
| Internet Gateway/Public IP | 직접 양방향 통신 | 노출면 증가 |
| Tunnel | 인바운드 포트 개방 불필요 | 브로커/프록시 계층 의존 |
