# Principle: 스키마 이력과 배포 순서

**핵심 질문**: 코드와 DB 상태는 왜 같은 방식으로 롤백되지 않는가?

## 한 문장 정의

스키마 이력과 배포 순서는 애플리케이션 코드는 버전 전환이 쉽지만 DB schema와 데이터는 변경 이력이 누적되는 상태이므로, migration 이력 관리와 하위 호환 배포 순서가 필요하다는 원리.

---

## 판단 기준

```text
Code
  - artifact 교체 가능
  - rollback 상대적으로 쉬움

Database schema/data
  - 운영 상태에 누적
  - 이미 적용된 변경은 그대로 남음
  - rollback보다 fix-forward가 기본
```

---

## 실무 기준

- 적용된 migration 파일은 수정하지 않는다.
- 변경은 새 version으로 forward한다.
- schema 변경은 expand-contract로 나눈다.
- 운영 DDL은 lock과 테이블 크기를 먼저 확인한다.
- 각 환경의 schema history를 비교 가능하게 둔다.
