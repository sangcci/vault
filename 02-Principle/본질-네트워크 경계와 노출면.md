# Principle: 네트워크 경계와 노출면

**핵심 질문**: 외부와 통신해야 하지만 어디까지 외부에 열어야 하는가?

## 한 문장 정의

네트워크 경계와 노출면은 인바운드·아웃바운드·프록시·터널 계층을 분리해, 필요한 통신만 허용하고 공격자가 직접 닿는 면을 최소화하는 원리.

---

## 해결하는 문제

- Cloudflare Tunnel 환경에서 fail2ban으로 공격자 IP를 차단하지 못하는 문제
- 프라이빗 서버는 외부 API를 호출해야 하지만 외부에서 직접 접근되면 안 되는 문제
- staging/admin/monitoring 서비스를 편의상 열었다가 스캐너에 노출되는 문제
- L3/L4 source IP와 L7 client IP를 혼동하는 문제

---

## 깨지는 상황

```text
Tunnel 사용
  ↓
실제 client IP는 HTTP header에 존재
  ↓
iptables는 Cloudflare/cloudflared source IP만 봄
  ↓
fail2ban 차단 위치가 맞지 않음
```

또는 다음처럼 노출면이 커진다.

```text
staging / grafana / prometheus 직접 공개
  ↓
자동화 봇이 .env, .git, actuator 탐색
  ↓
인증/차단이 없으면 내부 정보 노출 위험
```

---

## 판단 기준

- 인바운드가 꼭 필요한 서비스인지, 아웃바운드 터널로 충분한지 먼저 나눈다.
- 프라이빗 서버가 외부 API만 호출하면 NAT Gateway/SNAT로 충분하다.
- 외부 사용자가 내부 서비스에 접근해야 하지만 포트를 열 수 없으면 Tunnel을 검토한다.
- Tunnel/Proxy 환경에서는 IP 차단을 origin iptables가 아니라 edge/WAF/L7 계층에서 처리한다.
- monitoring, admin, staging 경로는 기본적으로 인증 또는 접근 제한을 둔다.
- 실제 클라이언트 IP가 어느 계층에서 보이는지 확인한 뒤 차단 도구를 고른다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 직접 공인 IP 노출 | 단순한 네트워크 구조 | 공격 노출면 증가 |
| NAT Gateway | 아웃바운드 허용, 인바운드 차단 | 비용, 외부 직접 접근 불가 |
| Cloudflare Tunnel | 포트 개방 불필요, edge 보호 | Cloudflare 의존, IP 차단 계층 변경 |
| WAF/Access | edge에서 조기 차단 | 정책 관리 필요 |
| nginx origin 차단 | 세밀한 path 제어 | 요청이 origin까지 도달 |
