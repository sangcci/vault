# Principle: 서브쿼리 변환과 반복 실행 경계

**핵심 질문**: 서브쿼리는 한 번 실행되는가, 바깥 row마다 실행되는가?

## 한 문장 정의

서브쿼리 변환과 반복 실행 경계는 SQL의 하위 SELECT가 planner에 의해 한 번 실행되는 값, join으로 변환되는 존재성 검사, 또는 outer row마다 반복되는 작업으로 달라질 수 있다는 원리.

---

## 해결하는 문제

- 상관 서브쿼리가 row마다 반복 실행되어 조회가 느린 문제
- `IN`, `EXISTS`, `NOT EXISTS`가 일반 JOIN과 어떻게 다른지 헷갈리는 문제
- 괄호 안 subquery가 항상 먼저 실행된다고 오해하는 문제
- `SubPlan loops`를 보지 않고 서브쿼리 비용을 과소평가하는 문제

---

## 판단 기준

```text
InitPlan
  - outer row와 독립
  - 한 번 실행 후 parameter로 사용

SubPlan
  - outer row 평가 중 호출
  - correlated 조건이 있으면 loops 증가 가능

Semi Join
  - EXISTS / IN의 존재 여부 검사
  - inner row를 결과에 곱하지 않음

Anti Join
  - NOT EXISTS의 부재 검사
  - matching inner row가 없는 outer만 반환
```

---

## 진단 포인트

- `EXPLAIN ANALYZE`에서 `SubPlan`의 `loops`를 본다.
- `InitPlan`인지 `SubPlan`인지 구분한다.
- `EXISTS`, `IN`, `NOT EXISTS`가 Semi/Anti Join으로 변환됐는지 본다.
- `NOT IN`은 NULL 포함 시 기대와 다른 결과가 나올 수 있음을 확인한다.
- 반복 실행이 크면 JOIN, 사전 집계, CTE, derived table로 바꿀 수 있는지 검토한다.

---

## 트레이드오프

서브쿼리는 의도를 잘 드러내지만, planner가 변환하지 못하면 반복 실행 비용이 숨어 있을 수 있다. 반대로 JOIN으로 무조건 바꾸면 중복 row가 늘거나 집계 단위가 바뀔 수 있다.
