# Principle: 공유 자원 점유와 대기열

**핵심 질문**: 제한된 자원을 오래 붙잡으면 왜 전체 시스템의 지연과 장애로 번지는가?

## 한 문장 정의

공유 자원 점유와 대기열은 **자원 수보다 사용 요청이 많거나 점유 시간이 길어질 때, 남은 요청이 줄을 서면서 지연시간과 timeout이 급격히 증가하는 구조**다.

---

## 해결하는 문제

이 본질은 다음 문제를 하나의 언어로 설명한다.

```text
- DB connection pool 고갈
- thread pool 고갈
- lock wait 증가
- HTTP client connection pool 대기
- queue backlog 증가
- CPU runnable thread 증가
```

공통 구조:

```text
동시 수요 × 점유 시간 > 자원 수 × 허용 대기 시간
        ↓
대기열 증가
        ↓
latency 증가
        ↓
timeout / retry / 장애 전파
```

---

## 깨지는 상황

자원 수만 보고 안전하다고 판단할 때 깨진다.

```text
pool size = 30
평균 처리 시간 = 100ms
  → 초당 약 300개 처리 가능해 보임

외부 API 지연으로 처리 시간 = 3s
  → 같은 pool size로 초당 약 10개 수준까지 감소
  → 나머지 요청은 pending queue로 밀림
```

문제는 자원이 부족한 것이 아니라, **점유 시간이 길어진 상태에서 유입량이 유지되는 것**이다.

```text
외부 API 지연
  → DB connection idle 점유 시간 증가
  → active connection max 도달
  → pending queue 증가
  → acquire timeout
  → client retry
  → 유입량 추가 증가
  → 더 빠른 고갈
```

---

## 판단 기준

공유 자원 문제를 볼 때는 항상 세 값을 같이 본다.

```text
1. 자원 수
   - pool size
   - worker thread 수
   - lock 대상 수

2. 점유 시간
   - transaction duration
   - lock hold time
   - external API latency
   - query duration

3. 동시 수요
   - RPS
   - concurrent request
   - retry traffic
   - batch fan-out
```

진단 질문:

```text
대기열이 생겼는가?
점유 시간이 늘었는가?
자원 수가 max에 닿았는가?
upstream retry가 유입량을 더 키우는가?
```

해결도 세 방향으로 나뉜다.

```text
자원 수 늘리기
  → pool size, replica, worker 증가

점유 시간 줄이기
  → transaction 축소, slow query 개선, timeout 단축

동시 수요 줄이기
  → rate limit, queue, backpressure, bulkhead
```

---

## 트레이드오프

```text
자원 수 증가
  장점: 빠른 완화 가능
  단점: 비용 증가, downstream 과부하, 근본 원인 은폐

점유 시간 감소
  장점: 같은 자원으로 처리량과 tail latency 개선
  단점: 코드 경계 재설계 필요

동시 수요 제한
  장점: 장애 전파 차단
  단점: 일부 요청 지연/거절, UX 조정 필요
```

중요한 점은 pool size를 늘리는 것이 항상 해결책은 아니라는 것이다. 점유 시간이 외부 장애 때문에 늘어난 상황에서는 자원을 더 크게 잡아도 장애 전파 시점만 늦출 수 있다.
