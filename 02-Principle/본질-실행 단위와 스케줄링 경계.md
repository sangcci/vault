# Principle: 실행 단위와 스케줄링 경계

**핵심 질문**: 프로그램, 프로세스, 스레드, CPU는 각각 무엇을 실행 단위로 보는가?

## 한 문장 정의

실행 단위와 스케줄링 경계는 작업이 프로그램·프로세스·소프트웨어 스레드·하드웨어 스레드로 표현되는 계층이 다르며, 실제 실행 가능성은 OS 스케줄러와 CPU 실행 슬롯의 경계에서 결정된다는 원리.

---

## 해결하는 문제

- 스레드를 많이 만들었는데 처리량이 늘지 않고 문맥 교환만 증가하는 문제
- 소프트웨어 스레드 수와 실제 병렬 실행 수를 혼동하는 문제
- Process, Thread, PCB, Scheduler를 각각 별도 암기 대상으로만 보는 문제
- 프로세스 격리와 스레드 공유의 차이를 성능/안정성 기준으로 판단하는 문제

---

## 판단 기준

```text
Program
  - 디스크의 실행 파일

Process
  - 실행 중인 프로그램의 전체 context
  - 주소 공간, 열린 파일, CPU 상태

PCB / task_struct
  - OS가 process/thread를 관리하기 위한 metadata

Software Thread
  - OS scheduler가 다루는 runnable 실행 흐름

Hardware Thread
  - CPU가 실제 동시에 실행할 수 있는 슬롯
```

---

## 진단 포인트

- runnable thread 수가 logical CPU 수보다 과도하게 많은가?
- 작업이 CPU-bound인가 I/O-bound인가?
- 프로세스 격리가 필요한가, 스레드 공유 메모리가 필요한가?
- thread pool이 작업 유형별로 분리되어 있는가?
- context switch와 run queue metric이 증가하는가?

---

## 트레이드오프

프로세스는 격리와 안정성이 좋지만 통신/전환 비용이 크다. 스레드는 공유가 쉽고 가볍지만 동기화와 경합 문제가 생긴다. 하드웨어 스레드 수를 넘는 실행 단위는 병렬성이 아니라 스케줄링 대기열을 만든다.
