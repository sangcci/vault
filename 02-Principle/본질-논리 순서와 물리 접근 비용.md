# Principle: 논리 순서와 물리 접근 비용

**핵심 질문**: 논리적으로는 같은 조건인데 왜 실제 실행 비용은 크게 달라지는가?

## 한 문장 정의

SQL의 논리 조건과 정렬 기준은 사용자가 원하는 결과를 표현하고, 실제 비용은 DB가 page와 tuple을 어떤 물리 순서로 접근하는지에 의해 결정된다.

---

## 해결하는 문제

- SQL 문장만 보고 실행 비용을 예측하는 문제
- 인덱스의 정렬된 키 순서와 heap의 물리 저장 순서를 같은 것으로 착각하는 문제
- `ORDER BY`, `WHERE`, `JOIN`이 실제로 어떤 page 접근과 memory/disk I/O로 바뀌는지 놓치는 문제

---

## 깨지는 상황

```text
논리 조건: WHERE boarding_date = '2025-09-11'
  ↓
B-tree index에서는 키가 정렬되어 있음
  ↓
하지만 heap row는 물리적으로 흩어져 있음
  ↓
TID 순서대로 page 892 → page 12 → page 457 접근
  ↓
랜덤 I/O 증가
```

논리적으로는 “같은 날짜를 찾는다”는 단순 조건이지만, 물리적으로는 많은 page를 건너뛰며 접근할 수 있다.

---

## 판단 기준

- 인덱스 키 순서가 곧 heap 저장 순서라고 가정하지 않는다.
- `Index Scan`이 느리면 매칭 row 수와 heap page 접근 분포를 함께 본다.
- `Bitmap Heap Scan`은 흩어진 TID를 page 단위로 모아 접근 비용을 줄이는 중간 전략으로 본다.
- `Seq Scan`은 무식한 방식이 아니라 물리 page를 순차로 읽는 전략이다.
- `EXPLAIN (ANALYZE, BUFFERS)`로 논리 조건이 실제 page 접근으로 어떻게 내려갔는지 확인한다.

---

## 트레이드오프

| 전략 | 물리 접근 특성 | 유리한 상황 |
|---|---|---|
| Seq Scan | heap page를 처음부터 끝까지 순차 접근 | 대부분의 row를 읽을 때 |
| Index Scan | index 탐색 후 TID로 heap 랜덤 접근 | 극소수 row를 찾을 때 |
| Bitmap Heap Scan | TID를 모아 page 순서로 heap 접근 | 중간 규모 row를 찾을 때 |
