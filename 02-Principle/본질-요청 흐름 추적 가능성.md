# Principle: 요청 흐름 추적 가능성

**핵심 질문**: 여러 스레드와 서비스에 흩어진 로그를 어떻게 하나의 요청으로 다시 묶을 수 있는가?

## 한 문장 정의

요청 흐름 추적 가능성은 요청마다 일관된 식별자를 생성·전파·기록해, 분산된 로그와 span을 하나의 사건 흐름으로 재구성할 수 있게 하는 원리.

---

## 해결하는 문제

- 동시 요청 로그가 섞여 장애 원인을 추적하기 어려운 문제
- MSA에서 어느 서비스 구간이 실패했는지 찾기 어려운 문제
- 비동기 실행에서 MDC/trace context가 끊기는 문제
- 로그는 많지만 요청 단위로 필터링할 수 없는 문제

---

## 깨지는 상황

```text
request A/B/C 동시 처리
  ↓
thread pool에서 실행 순서 섞임
  ↓
공유 로그 스트림에 append
  ↓
traceId 없음
  ↓
장애 발생 후 요청 흐름 재구성 불가
```

또는 서비스 간 호출에서 식별자가 끊긴다.

```text
API Gateway(traceId=abc)
  ↓ header 미전파
OrderService(traceId 없음)
  ↓
PaymentService(traceId 없음)
```

---

## 판단 기준

- 요청 진입점에서 traceId/requestId를 생성하거나 외부 trace context를 수용한다.
- 모든 로그에 traceId, service, endpoint, status, elapsed 같은 최소 필드를 포함한다.
- HTTP, message queue, async task 경계에서 context 전파를 명시한다.
- MDC를 쓴다면 요청 종료 시 반드시 clear하고, 스레드 풀 전환 시 복사/복원한다.
- 로그 저장소가 traceId 필드로 검색 가능한 구조화 로그를 받도록 한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 단순 requestId | 구현 쉬움, 로그 필터링 가능 | span별 지연 분석은 약함 |
| W3C Trace Context | 서비스 간 표준 전파 | 모든 경계에서 구현 필요 |
| OpenTelemetry | traces/logs/metrics 연동 | 설정·샘플링·collector 운영 필요 |
| 모든 요청 trace 저장 | 분석 정밀도 높음 | 저장 비용과 개인정보 리스크 |
| 샘플링 | 비용 절감 | 낮은 빈도 장애 누락 가능 |
