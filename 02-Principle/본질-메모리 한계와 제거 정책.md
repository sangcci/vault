# Principle: 메모리 한계와 제거 정책

**핵심 질문**: 저장 공간이 가득 찼을 때 무엇을 버릴 것인가?

## 한 문장 정의

메모리 한계와 제거 정책은 유한한 저장 공간에서 모든 항목을 보존할 수 없을 때, 접근 최근성·빈도·만료 시간·중요도 기준으로 제거 대상을 정해야 한다는 원리.

---

## 해결하는 문제

- Redis 메모리 한도에 도달하자 중요 키가 사라지거나 쓰기가 실패하는 문제
- LRU/LFU/Clock 같은 교체 알고리즘을 이름만 외우고 적용 조건을 놓치는 문제
- 캐시 키와 세션/락/카운터 같은 상태 키를 같은 eviction 정책에 맡기는 문제
- 캐시 hit rate와 데이터 생존성 요구가 충돌하는 문제

---

## 판단 기준

```text
사라져도 원본에서 복구 가능한가?
  ├─ 예: cache key → eviction 가능
  └─ 아니오: session/lock/business state → eviction 위험

최근성이 중요한가?
  → LRU / approximate LRU

장기 인기 키가 중요한가?
  → LFU / TinyLFU

TTL 있는 임시 키만 제거할 것인가?
  → volatile-* 정책

모든 키가 캐시인가?
  → allkeys-* 정책 가능
```

---

## 알고리즘 감각

```text
LRU
  - 최근에 안 쓴 것을 버림
  - temporal locality에 강함
  - 순차 스캔에 약함

LFU
  - 적게 쓴 것을 버림
  - 장기 인기 콘텐츠에 강함
  - 오래된 인기 키가 버티는 오염 가능

Clock / approximate LRU
  - 완전 LRU 비용을 줄인 근사
  - 정확도보다 운영 비용 절감
```

---

## 트레이드오프

교체 정책은 메모리 부족을 해결하지만, 어떤 데이터가 비즈니스적으로 중요하다는 사실은 모른다. 따라서 eviction을 고르기 전에 Redis 인스턴스와 key space를 용도별로 나누는 것이 먼저다.
