# Principle: 컴파일 타임 타입과 런타임 객체의 분리

**핵심 질문**: Java에서 타입 검사는 언제 끝나고, 실제 구현 선택은 언제 일어나는가?

## 한 문장 정의

컴파일 타임 타입과 런타임 객체의 분리는 Java가 컴파일 시점에는 선언 타입과 제네릭 정보로 타입 안전성을 검사하고, 런타임에는 실제 객체와 virtual dispatch로 일부 메서드 구현을 선택한다는 원리.

---

## 해결하는 문제

- 제네릭 타입 `T`가 런타임에도 그대로 남아 있다고 믿는 문제
- overload와 override 선택 시점을 혼동하는 문제
- 필드와 static method가 다형적으로 동작한다고 기대하는 문제
- 런타임 타입 분기에 `List<String>` 같은 parameterized type을 쓰려는 문제

---

## 판단 기준

```text
컴파일 타임
  - overload 선택
  - 필드 접근 타입 결정
  - static method 선택
  - generic type checking
  - type parameter erasure

런타임
  - 실제 객체 존재
  - override method dispatch
  - vtable/itable 기반 구현 선택
```

---

## 진단 포인트

- 현재 문제가 overload인지 override인지 구분한다.
- 런타임에 필요한 타입 정보가 소거되는 제네릭 타입인지 확인한다.
- `Class<T>`나 타입 토큰이 필요한 API인지 판단한다.
- 필드 접근 대신 메서드를 통해 다형성을 표현해야 하는지 본다.

---

## 트레이드오프

타입 소거는 기존 JVM과 바이트코드 호환성을 지키면서 제네릭 타입 검사를 제공한다. 대신 런타임 타입 정보가 필요한 작업에는 추가 타입 토큰이나 다른 설계가 필요하다.

## 참고
