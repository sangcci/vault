# Principle: 선언 위치의 함수 변환

**핵심 질문**: `pay = log(auth(pay))`처럼 함수를 감싸는 코드를 왜 `@decorator` 문법으로 선언 바로 위에 적는가?

## 한 문장 정의

언어 decorator는 함수·클래스 또는 클래스 멤버(메서드·필드·접근자)의 정의를 받아 다른 구현으로 바꾸거나 부가 정보를 붙이는 문법이다. 변환 규칙을 선언 위치에 모아 여러 wrapper에 흩어진 의도를 읽기 쉽게 만든다.

---

## 먼저 구분할 것

`@decorator`라는 문법, GoF Decorator 패턴, Proxy 패턴은 이름과 모양이 겹칠 수 있지만 같은 개념은 아니다.

```text
언어 decorator
  @log
  function pay() {}
  → 정의 시점에 pay를 변환하거나 교체

GoF Decorator
  LoggingPaymentProcessor(CardPaymentProcessor)
  → 같은 인터페이스 객체를 감싸 기능 추가

Proxy
  caller → proxy → target
  → target 접근을 대리하거나 통제
```

언어 decorator가 wrapper를 반환하면 GoF Decorator 패턴과 비슷한 구조를 만들 수 있다. 하지만 metadata 등록, 필드 초기화, 라우트 등록처럼 객체를 감싸지 않는 decorator도 많다.

---

## 왜 등장했나

일급 객체를 지원하는 언어에서는 함수를 값처럼 넘기고, 받아 다른 함수로 바꿀 수 있다. 그래서 로깅, 인증, 캐싱 같은 횡단 관심사를 wrapper로 만들기 쉽다.

```python
def log(fn):
    def wrapped(*args, **kwargs):
        print("before")
        result = fn(*args, **kwargs)
        print("after")
        return result
    return wrapped

pay = log(auth(pay))
```

기능이 적을 때는 이 방식이 분명하다. 하지만 wrapper가 쌓이면 어떤 함수에 무엇이 적용됐는지 알기 어려워진다. decorator 문법은 변환 규칙을 함수 선언 가까이에 둔다.

```python
@log
@auth
def pay():
    ...

# pay = log(auth(pay))
```

> "The current method for transforming functions and methods … is awkward and can lead to code that is difficult to understand." — [PEP 318](https://peps.python.org/pep-0318/)

> "A solution to this problem is to move the transformation of the method closer to the method’s own declaration." — [PEP 318](https://peps.python.org/pep-0318/)

---

## 판단 기준

- 함수 자체를 받아 wrapper로 바꾸는 일은 일급 객체 모델에서 자연스럽다. decorator 문법이 있다고 해서 Proxy 기능인 것은 아니다.
- 전후 처리를 추가하고 원래 호출 의미를 유지하려면 wrapper decorator를 쓴다.
- 접근 권한, lazy loading, 원격 호출처럼 target 접근 자체를 통제하려면 Proxy의 목적에 가깝다.
- Java annotation은 메타데이터다. annotation만으로 실행 로직이 생기지 않는다. Spring 같은 프레임워크가 이를 해석해 proxy/interceptor를 구성할 때 행동이 생긴다.
- JavaScript decorator는 TypeScript legacy decorator와 ECMAScript decorator의 규칙이 다를 수 있다. 프로젝트 설정과 런타임 지원을 먼저 확인해야 한다.
