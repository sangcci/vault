# Principle: 인덱스 선택도와 접근 경로

**핵심 질문**: 인덱스가 있는데도 왜 DB는 테이블을 전부 읽거나 느리게 실행할까?

## 한 문장 정의

인덱스 성능은 존재 여부가 아니라 조건이 후보 row와 heap page 접근을 얼마나 줄이는지, 즉 선택도와 접근 경로의 비용으로 결정된다.

---

## 해결하는 문제

- 인덱스를 추가했는데도 조회가 느린 문제
- `Seq Scan`을 무조건 나쁜 실행 계획으로 오해하는 문제
- `Index Scan`을 탔는데도 heap 랜덤 I/O와 Filter 비용 때문에 느린 문제
- `EXPLAIN`에서 scan 방식만 보고 실제 병목을 놓치는 문제

---

## 깨지는 상황

```text
카디널리티 낮은 컬럼에 단일 인덱스 추가
  ↓
조건에 맞는 row가 전체의 상당 부분
  ↓
Index Scan 선택 시 heap page 랜덤 접근 폭증
  또는 Seq Scan 선택
  ↓
"인덱스를 만들었는데 왜 안 빨라지지?"
```

인덱스는 정답 위치를 바로 알려주는 장치가 아니라, 후보 위치를 줄이는 장치다. 후보가 충분히 줄지 않으면 인덱스 탐색 비용과 heap 접근 비용이 오히려 부담이 된다.

---

## 판단 기준

- 매칭 row가 극소수이면 `Index Scan`이 유리하다.
- 매칭 row가 중간 규모이면 TID를 모아 heap page 순서로 접근하는 `Bitmap Heap Scan`이 유리할 수 있다.
- 매칭 row가 대부분이면 `Seq Scan`이 더 단순하고 빠를 수 있다.
- `Index Cond`는 heap 접근 전 후보를 줄이는 조건이고, `Filter`는 tuple을 읽은 뒤 버리는 조건이다.
- `Rows Removed by Filter`가 크면 인덱스를 탔어도 읽고 버리는 비용이 크다는 뜻이다.
- `Buffers: shared read`가 크면 디스크/OS cache/shared buffer 경로의 page 적재 비용을 의심한다.

```text
매칭 row 비율
0%                    50%                  100%
│──────────────────────┼─────────────────────│
Index Scan ←──────────┤
                       ├── Bitmap Scan ──┤
                                       ├──── Seq Scan ──────→
```

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 단일 인덱스 | 간단한 조건 탐색 | 복합 조건에서 Filter가 남을 수 있음 |
| 복합 인덱스 | 여러 조건을 탐색 단계로 내릴 수 있음 | 컬럼 순서와 쿼리 패턴에 묶임 |
| Partial Index | 작은 인덱스로 자주 쓰는 subset 최적화 | 조건이 맞지 않으면 사용 불가 |
| Covering Index | heap 접근 감소 | 인덱스 크기와 쓰기 비용 증가 |
| Seq Scan 허용 | 대량 조회에서 단순하고 빠름 | 소량 조회에서는 전체 scan 비용 발생 |
