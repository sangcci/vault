# Principle: 트랜잭션 경계

**핵심 질문**: 어떤 작업까지 하나의 원자적 단위로 묶고, 어떤 작업은 트랜잭션 밖으로 분리해야 하는가?

## 한 문장 정의

트랜잭션 경계는 **함께 성공하거나 함께 실패해야 하는 DB 상태 변경의 최소 범위를 정하고, 느리거나 되돌릴 수 없는 외부 작업을 그 범위에서 분리하는 판단 기준**이다.

---

## 해결하는 문제

트랜잭션은 데이터 일관성을 지키기 위한 도구지만, 범위가 넓어지면 다른 장애를 만든다.

```text
범위가 너무 좁음
  → 중간 상태 노출
  → 부분 성공
  → 데이터 불일치

범위가 너무 넓음
  → lock/connection 점유 시간 증가
  → 외부 장애가 DB 자원 고갈로 전파
  → rollback 불가능한 외부 작업과 정합성 충돌
```

## 깨지는 상황

가장 흔한 실패는 `@Transactional`을 usecase 전체에 넓게 붙이고, 그 안에 외부 I/O를 넣는 것이다.

```text
@Transactional
  ├─ DB write
  ├─ 외부 API 호출 대기
  ├─ 파일 처리
  └─ DB write

결과:
외부 대기 시간 동안 DB connection/lock이 같이 점유됨
```

특히 결제, 배송, 알림, 파일 업로드처럼 외부 시스템이 끼면 DB rollback만으로 전체 작업을 되돌릴 수 없다.

```text
외부 결제 성공
  ↓
DB commit 실패
  ↓
DB는 실패, 외부 시스템은 성공
  ↓
보상/재시도/멱등성 필요
```

---

## 판단 기준

트랜잭션 안에 넣을 것:

```text
- 같은 DB 안에서 함께 성공/실패해야 하는 상태 변경
- aggregate 상태 변경과 저장
- 같은 commit 기준으로 맞춰야 하는 outbox/audit log 기록
- 동시성 제어가 필요한 읽기-수정-쓰기 구간
```

트랜잭션 밖으로 빼야 할 것:

```text
- 외부 HTTP API 호출
- 파일 업로드/다운로드
- 오래 걸리는 계산
- 사용자 입력 대기
- retry가 필요한 네트워크 작업
- DB rollback으로 되돌릴 수 없는 부작용
```

판단 흐름:

```text
이 작업은 DB rollback으로 되돌릴 수 있는가?
  ├─ YES → 같은 원자 단위인지 판단
  └─ NO  → transaction 밖으로 분리하고 보상/재시도 설계

이 작업은 오래 걸리거나 외부 상태에 의존하는가?
  ├─ YES → transaction 밖으로 분리
  └─ NO  → 필요한 최소 범위만 transaction 안에 둠
```

---

## 트레이드오프

```text
큰 트랜잭션
  장점: 코드가 단순하고 즉시 일관성처럼 보인다.
  단점: lock/connection 점유 시간이 길고 외부 장애가 내부 자원 고갈로 전파된다.

작은 트랜잭션
  장점: 자원 점유 시간이 짧고 장애 격리가 쉽다.
  단점: 상태 전이, 재시도, 보상, 최종 일관성 설계가 필요하다.
```

실무에서는 보통 다음 형태가 더 안전하다.

```text
짧은 DB transaction
  → 상태 기록 / outbox 저장
  → commit
  → 외부 API 호출
  → 결과 반영용 짧은 DB transaction
  → 실패 시 재시도 또는 보상
```
