# Principle: 공유 가변 상태와 원자 경계

**핵심 질문**: 여러 실행 흐름이 같은 값을 바꿀 때 결과는 왜 실행 순서에 따라 달라지는가?

## 한 문장 정의

공유 가변 상태와 원자 경계는 동시에 접근 가능한 변경 상태를 다룰 때, 의미상 하나인 판단과 변경을 쪼개지지 않는 경계 안에 넣어야 한다는 원리.

---

## 해결하는 문제

- `count++`가 동시 요청에서 누락되는 문제
- `containsKey` 후 `put`이 중복 생성이나 덮어쓰기를 만드는 문제
- thread-safe 컬렉션을 써도 비즈니스 불변식이 깨지는 문제
- CAS 기반 로직에서 값만 같고 이력이 다른 ABA 문제를 놓치는 문제

---

## 깨지는 상황

```text
Read-Modify-Write
read old
  ↓ race window
calculate new
  ↓ race window
write new
```

```text
Check-then-Act
check condition
  ↓ race window
act based on old condition
```

두 패턴의 공통점은 “확인한 상태가 실행 시점에도 유효하다”는 보장이 없다는 점이다.

---

## 판단 기준

- 공유되는가?
- 변경 가능한가?
- 동시에 접근 가능한가?
- 여러 단계가 의미상 하나의 동작인가?
- 값뿐 아니라 이력도 중요한가?

네 조건이 모이면 원자 경계가 필요하다.

```text
공유 + 변경 가능 + 동시 접근 + 복합 의미
  ↓
원자 API / lock / transaction / immutable redesign 필요
```

---

## 해결 방식

| 방식 | 적합한 상황 | 주의 |
|---|---|---|
| Atomic API | 짧은 단일 변수 갱신 | 복합 불변식에는 부족 |
| `computeIfAbsent`, `putIfAbsent` | key 단위 map 불변식 | mapping function 부작용 주의 |
| Lock / synchronized | 여러 상태를 함께 보호 | 경합/교착 가능 |
| Version stamping | ABA처럼 이력이 중요한 경우 | 상태 모델 증가 |
| 불변 객체 교체 | 읽기 많고 변경 적음 | 복사 비용 |
| DB constraint/transaction | 최종 정합성 방어 | DB 경합/격리 비용 |
