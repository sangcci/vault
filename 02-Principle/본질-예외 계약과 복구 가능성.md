# Principle: 예외 계약과 복구 가능성

**핵심 질문**: 어떤 실패를 호출자의 공개 계약으로 드러내야 하는가?

## 한 문장 정의

예외 계약과 복구 가능성은 호출자가 합리적으로 복구할 수 있는 실패만 checked exception 같은 공개 계약으로 드러내고, 복구할 수 없는 기술 실패나 프로그래밍 오류는 경계 안에서 변환하거나 unchecked로 다룬다는 원리.

---

## 해결하는 문제

- checked exception이 호출 체인 전체를 오염시키는 문제
- 기술 예외가 도메인 서비스 인터페이스 밖으로 새는 문제
- Spring 트랜잭션 rollback 기대와 Java checked exception 철학이 충돌하는 문제
- 예외를 단순히 checked/unchecked 문법으로만 구분하는 문제

---

## 판단 기준

```text
Checked Exception으로 드러낼 후보
  - 호출자가 실제 복구 가능
  - API 계약으로 실패 처리를 강제해야 함
  - 예: 재시도 가능한 외부 입력/파일 선택 실패 등

Unchecked Exception 후보
  - 호출자가 그 자리에서 복구 불가
  - 프로그래밍 오류 또는 깨진 불변식
  - 상위 공통 handler에서 처리
  - 예: 잘못된 인자, 도메인 규칙 위반, 인프라 실패 래핑
```

---

## 진단 포인트

- catch한 위치에서 실제 복구하는지 확인한다.
- 단순히 다시 throws만 하는 checked exception인지 본다.
- 인터페이스가 JDBC, 파일, 네트워크 같은 기술 타입을 노출하는지 확인한다.
- 예외 변환 시 원인 예외를 보존하는지 확인한다.
- 트랜잭션 rollback 정책과 예외 계층이 맞는지 본다.

---

## 트레이드오프

Checked exception은 실패 처리를 누락하지 않게 강제하지만, 복구 불가능한 실패까지 공개 계약으로 만들면 추상화가 깨진다. Unchecked exception은 호출 체인을 깨끗하게 유지하지만, 문서화와 공통 처리 정책이 없으면 예측하기 어렵다.
