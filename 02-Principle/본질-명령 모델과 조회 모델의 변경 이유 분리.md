# Principle: 명령 모델과 조회 모델의 변경 이유 분리

**핵심 질문**: 이 모델은 규칙을 보호하려고 바뀌는가, 화면을 맞추려고 바뀌는가?

## 한 문장 정의

명령 모델과 조회 모델의 변경 이유 분리는 상태 변경 모델은 업무 규칙과 불변식을 보호하고, 조회 모델은 화면 형태와 성능 요구에 맞추되, 둘의 변경 이유가 다를 때만 분리하는 원리.

---

## 판단 기준

```text
Command model
  - 상태 변경
  - 규칙 검증
  - 불변식 보호
  - transaction boundary

Query model
  - 화면 응답
  - join / filter / sort / page
  - projection
  - read performance
```

---

## 실무 기준

- 단순 CRUD에는 CQRS를 과하게 적용하지 않는다.
- 목록/상세 조회가 도메인 모델을 오염시키면 분리를 고려한다.
- 쓰기 저장소와 조회 Finder/QueryPort를 역할별로 나눈다.
- read model 정합성 지연이 생기면 API 계약에 명시한다.
- 분리 기준은 데이터 종류가 아니라 변경 이유다.
