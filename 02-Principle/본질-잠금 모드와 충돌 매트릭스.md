# Principle: 잠금 모드와 충돌 매트릭스

**핵심 질문**: 어떤 DB 명령은 왜 다른 명령을 막고, 어떤 명령은 같이 실행되는가?

## 한 문장 정의

잠금 모드와 충돌 매트릭스는 DB 명령이 자원별 잠금 모드를 획득하고, 미리 정의된 충돌 규칙에 따라 동시 실행 가능 여부가 결정된다는 원리.

---

## 해결하는 문제

- 운영 중 인덱스 추가로 쓰기 요청이 막히는 문제
- WHERE 없는 UPDATE가 사실상 전체 쓰기 경합을 만드는 문제
- PostgreSQL에서 SELECT는 되는데 DML만 막히거나, 반대로 SELECT까지 막히는 이유를 구분하는 문제
- Row Lock과 Table Lock을 단순 이름이 아니라 충돌 범위로 이해하는 문제

---

## 판단 기준

```text
명령 실행
  ↓
DB가 자동으로 lock mode 획득
  ↓
이미 보유된 lock과 충돌 매트릭스 비교
  ↓
비충돌: 동시 실행
충돌: 대기
```

PostgreSQL 관점의 대표 차이:

```text
일반 SELECT
  → AccessShareLock
  → AccessExclusiveLock과만 충돌

INSERT/UPDATE/DELETE
  → RowExclusiveLock
  → 일반 CREATE INDEX의 ShareLock과 충돌

CREATE INDEX CONCURRENTLY
  → ShareUpdateExclusiveLock
  → 일반 DML과는 충돌하지 않음
```

---

## 진단 포인트

- `pg_locks`와 `pg_stat_activity`로 blocking PID를 확인한다.
- 어떤 SQL이 어떤 lock mode를 획득하는지 확인한다.
- lock이 row 단위인지 table 단위인지, 또는 row lock이 대량으로 확산되는지 본다.
- WHERE 없는 UPDATE/DELETE처럼 영향 row 수가 큰 쿼리는 사실상 테이블 전체 쓰기를 막을 수 있다.
- DDL은 실행 시간뿐 아니라 대기 중인 트랜잭션과 충돌 모드를 함께 본다.

---

## 트레이드오프

강한 잠금은 안전하지만 동시성을 줄인다. 약한 잠금은 동시성을 높이지만 더 많은 단계, 재검증, 실패 후 정리 절차를 요구한다. 운영 DB 변경은 잠금 강도와 대기 시간을 함께 설계해야 한다.
