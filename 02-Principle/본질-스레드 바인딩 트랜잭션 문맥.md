# Principle: 스레드 바인딩 트랜잭션 문맥

**핵심 질문**: Spring은 어떻게 여러 계층이 같은 트랜잭션 자원을 쓰게 만드는가?

## 한 문장 정의

스레드 바인딩 트랜잭션 문맥은 현재 Java thread에 Connection, EntityManager 같은 resource를 묶어 같은 실행 흐름 안에서 일관된 트랜잭션을 공유하게 하는 원리.

---

## 해결하는 문제

- save 호출을 try-catch로 감쌌는데 DB 제약 예외를 잡지 못하는 문제
- Service와 Repository가 서로 다른 Connection/EntityManager를 쓰면 트랜잭션 경계가 깨지는 문제
- 주입된 EntityManager가 singleton Bean에서 어떻게 안전하게 동작하는지 헷갈리는 문제
- `@Async`나 새 thread로 넘어가면 트랜잭션 문맥이 끊기는 문제

---

## 깨지는 상황

```text
@Transactional method
  ↓
현재 thread에 EntityManager/Connection bind
  ↓
Repository는 thread-bound resource 사용
  ↓
다른 thread로 이동
  ↓
ThreadLocal 문맥 없음
```

또는 flush/commit 시점을 놓친다.

```text
save()
  ↓
Persistence Context에 변경 등록
  ↓
commit 직전 flush
  ↓
DB 제약 예외 발생
```

---

## 판단 기준

- imperative Spring transaction은 현재 thread 기준으로 이해한다.
- Tomcat, Kafka listener, Scheduler, Batch 모두 “현재 thread”가 다를 뿐 원리는 같다.
- `@Async`, executor, 직접 만든 thread로 넘어가면 기존 transaction resource가 자동 전파되지 않는다.
- `@PersistenceContext`로 주입된 EntityManager는 보통 실제 EntityManager가 아니라 shared proxy다.
- JPA 예외 처리 위치를 정할 때는 save 시점이 아니라 flush/commit 시점을 확인한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| ThreadLocal 기반 transaction | 동기 코드에서 단순하고 빠름 | thread 전환 시 문맥 단절 |
| Shared EntityManager proxy | singleton Bean에서도 안전한 위임 | 실제 EntityManager와 proxy 구분 필요 |
| 명시적 flush | 예외 발생 위치 제어 | DB 왕복과 flush 비용 증가 |
| Reactive transaction | 비동기 문맥 대응 | Reactor Context 이해 필요 |
