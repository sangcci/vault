# Principle: 임계 구역과 활동성

**핵심 질문**: 공유 자원을 안전하게 보호하면서도 시스템이 멈추지 않게 하려면 무엇을 보장해야 하는가?

## 한 문장 정의

임계 구역과 활동성은 공유 자원 접근을 한 번에 하나로 제한하되, 대기 흐름이 무한히 막히거나 굶지 않도록 진행 조건까지 함께 설계해야 한다는 원리.

---

## 해결하는 문제

- race condition을 막으려고 락을 걸었더니 처리량이 급락하는 문제
- 여러 락을 서로 다른 순서로 잡아 deadlock이 생기는 문제
- spin, wait, park 상태가 늘어나 요청이 멈춘 것처럼 보이는 문제
- 안전성만 보고 liveness를 검증하지 않는 문제

---

## 깨지는 상황

```text
상호 배제만 확보
  ↓
데이터는 맞음
  ↓
하지만 모두 기다림 / 너무 오래 기다림 / 일부가 굶음
```

임계 구역 해결에는 세 가지 조건이 함께 필요하다.

```text
1. Mutual Exclusion: 동시에 들어오지 못하게 함
2. Progress: 들어갈 수 있으면 누군가는 진행해야 함
3. Bounded Waiting: 한 주체가 무한히 굶지 않아야 함
```

Deadlock은 보통 점유와 대기가 원형으로 연결될 때 생긴다.

```text
Thread A holds Lock A → waits Lock B
Thread B holds Lock B → waits Lock A
```

---

## 판단 기준

- 임계 구역 안에서 느린 I/O, DB, 외부 API, sleep을 수행하는가?
- 여러 lock을 잡는 코드가 전역 순서를 지키는가?
- lock 대기 시간이 전체 latency의 대부분인가?
- 무한 대기 대신 timeout, 취소, 재시도 경로가 있는가?
- 공정성이 필요한 자원인가, 처리량이 더 중요한 자원인가?

---

## 해결 방식

| 방식 | 얻는 것 | 비용/주의 |
|---|---|---|
| 임계 구역 최소화 | 경합 시간 감소 | 보호 범위 재검토 필요 |
| 락 순서 고정 | deadlock 예방 | 모든 코드 경로 일관성 필요 |
| timeout/tryLock | 무한 대기 방지 | 실패 처리 필요 |
| 공정 락 | starvation 완화 | 처리량 감소 가능 |
| 큐/단일 writer | 순서 단순화 | 지연과 backpressure 필요 |
| lock-free/CAS | blocking 감소 | ABA, 재시도 폭증 가능 |
