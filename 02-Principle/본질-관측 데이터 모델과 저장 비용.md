# Principle: 관측 데이터 모델과 저장 비용

**핵심 질문**: 왜 메트릭, 로그, 트레이스 도구는 서로 대체하기 어렵고 비용 구조도 다른가?

## 한 문장 정의

관측 도구의 비용과 검색 능력은 이름이 아니라 저장하는 데이터 모델, 인덱싱 범위, 조회 패턴에 의해 결정된다.

---

## 해결하는 문제

- 운영 모니터링 스택을 골랐지만 로그 검색과 메트릭 요구가 맞지 않는 문제
- Prometheus, Loki, Grafana, ELK를 같은 층위의 대체재로 오해하는 문제
- 비용 효율과 검색 자유도를 동시에 최대로 얻으려는 문제
- 장기 보관, 멀티테넌시, 전문 검색 요구를 단일 도구에 모두 기대하는 문제

---

## 깨지는 상황

```text
도구 이름 중심 선택
  ├─ Prometheus면 관측 다 되겠지
  ├─ Loki면 로그 검색 다 되겠지
  └─ Grafana면 저장도 해주겠지
        ↓
데이터 모델 불일치
        ↓
검색 한계 / 비용 폭증 / 대시보드 품질 저하
```

각 도구는 다루는 신호와 비용 최적화 방향이 다르다.

```text
Prometheus: numeric time series + label + pull scrape
Loki: log stream + label index + compressed chunk
ELK: document/index + full-text/search analytics
Grafana: data source query + dashboard/view
```

---

## 판단 기준

- 수치 알람과 구간 집계가 핵심이면 metrics/TSDB를 먼저 본다.
- 로그 본문 전문 검색과 필드 분석이 핵심이면 ELK 계열을 검토한다.
- 운영 로그 보관과 원인 확인이 핵심이고 비용을 줄이고 싶으면 Loki 계열을 검토한다.
- 여러 관측 저장소를 한 화면에서 연결해야 하면 Grafana 같은 view 계층을 둔다.
- 장기 보관, 전역 집계, 멀티테넌시가 중요하면 단일 Prometheus 뒤의 확장형 backend를 검토한다.
- label cardinality와 full-text index 범위를 비용의 핵심 변수로 본다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| Prometheus | 수치 시계열, 알람, exporter 생태계 | 로그 본문 검색 |
| Loki | 저비용 로그 보관, label 기반 탐색 | 강한 full-text 검색 |
| ELK | 검색·분석 자유도 | 색인 비용, 운영 복잡도 |
| Grafana | 여러 데이터 소스 시각화 | 원본 저장 품질은 보장하지 않음 |
| SaaS 관측 플랫폼 | 운영 부담 감소 | 비용, 벤더 종속성 |
