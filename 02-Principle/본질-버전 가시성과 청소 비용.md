# Principle: 버전 가시성과 청소 비용

**핵심 질문**: 읽기와 쓰기를 덜 막는 DB는 왜 오래된 row version을 청소해야 하는가?

## 한 문장 정의

버전 가시성과 청소 비용은 같은 논리 row의 여러 물리 version을 남겨 트랜잭션별 snapshot에 맞게 보여주되, 더 이상 보이지 않는 version을 나중에 회수해야 한다는 원리.

---

## 해결하는 문제

- 장기 트랜잭션 때문에 VACUUM이 dead tuple을 정리하지 못하는 문제
- UPDATE가 덮어쓰기라고 오해해 heap bloat 원인을 놓치는 문제
- snapshot이 오래 유지되면 과거 row version도 계속 보존되어야 하는 이유
- MVCC가 lock-free가 아니라 cleanup cost를 뒤로 미루는 구조라는 점

---

## 판단 기준

```text
UPDATE
  old version 종료 표시
  new version 생성

각 transaction snapshot
  → 어떤 version이 보이는지 결정

VACUUM
  → 아무 snapshot도 볼 수 없는 old version만 정리 가능
```

핵심은 “존재하는 row”와 “내 transaction에 보이는 row”가 다르다는 점이다.

```text
physical heap에는 old/new version이 같이 있을 수 있음
logical query는 snapshot 기준 하나만 봄
cleanup은 모든 snapshot의 가시성 경계 뒤에서만 가능
```

---

## 진단 포인트

- 오래 열린 transaction이 있는지 확인한다.
- `backend_xmin`이 오래된 세션을 찾는다.
- dead tuple 수와 autovacuum 실행 시점을 본다.
- 장기 cursor/batch/read-only transaction도 cleanup을 막을 수 있음을 확인한다.
- bloat 문제를 인덱스/쿼리 plan 문제와 분리해 본다.

---

## 트레이드오프

MVCC는 읽기와 쓰기의 직접 충돌을 줄여 처리량을 높인다. 대신 old version 저장 공간, VACUUM I/O, 장기 snapshot 관리라는 운영 비용을 만든다. 동시성을 공짜로 얻는 것이 아니라, 정리 시점과 비용을 뒤로 미루는 것이다.
