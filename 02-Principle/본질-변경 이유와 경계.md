# Principle: 변경 이유와 경계

**핵심 질문**: 같은 데이터를 다루는 코드는 항상 같은 경계에 있어야 하는가?

## 한 문장 정의

변경 이유와 경계는 코드, API, DTO, 모듈을 같은 데이터 기준이 아니라 같은 행위자와 같은 변경 이유 기준으로 묶어야 한다는 원리.

---

## 해결하는 문제

- 같은 데이터를 다룬다는 이유로 고객 API와 관리자 API를 합쳐 변경이 꼬이는 문제
- DTO 하나에 서로 다른 사용자와 권한의 필드가 누적되는 문제
- UI 화면 모양만 보고 조회 API를 묶었다가 V2/V3가 빠르게 늘어나는 문제
- 단순 데이터 참조와 도메인 의존을 구분하지 못해 결합도가 높아지는 문제

---

## 판단 기준

```text
같은 데이터인가?
  → 충분 조건 아님

같은 행위자인가?
같은 변경 요청자인가?
같은 권한/감사/트래픽/장애 영향인가?
같은 배포·운영 라이프사이클인가?
  → 다르면 경계 분리 검토
```

API 경계도 같은 원리다.

```text
/customer/products
  변경 이유: 고객 UX, 성능, 공개 스펙

/admin/products
  변경 이유: 운영 정책, CS, 권한, 감사 로그

/settlement/products
  변경 이유: 정산, 회계, 수수료
```

---

## 진단 포인트

- 한쪽 변경이 다른쪽 테스트/DTO/API 문서를 깨는가?
- URL prefix만 다르고 내부 DTO/service는 완전히 공유하는가?
- 권한과 감사 로그 요구가 다른데 같은 usecase에 들어 있는가?
- 상대 도메인의 객체/메서드를 직접 호출하는가, id/type 값만 참조하는가?
- 같은 화면이라는 이유로 변경 주기가 다른 데이터를 한 API에 묶었는가?

---

## 트레이드오프

경계를 나누면 중복과 조합 비용이 생긴다. 경계를 합치면 변경 이유가 다른 요구가 한 코드에 누적된다. 좋은 경계는 중복을 0으로 만드는 경계가 아니라 함께 바뀌는 것끼리 묶는 경계다.
