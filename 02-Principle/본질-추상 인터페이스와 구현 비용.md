# Principle: 추상 인터페이스와 구현 비용

**핵심 질문**: 같은 인터페이스를 구현해도 왜 성능과 제약은 달라지는가?

## 한 문장 정의

추상 인터페이스와 구현 비용은 `List`, `Map`처럼 같은 추상 계약을 제공하더라도 내부 자료구조와 런타임 구현 방식에 따라 접근 비용, 메모리 배치, 순서 보장, 타입 정보 제약이 달라진다는 원리.

---

## 해결하는 문제

- `List`면 ArrayList와 LinkedList가 성능도 비슷하다고 착각하는 문제
- `Map`이면 HashMap, LinkedHashMap, TreeMap의 비용 모델을 무시하는 문제
- 제네릭 타입이 컴파일 타임 추상화라는 점을 놓치는 문제
- API 추상화 뒤의 구현 비용을 보지 않고 선택하는 문제

---

## 판단 기준

```text
Interface
  - 사용자가 기대하는 연산 계약
  - add/get/put/remove 같은 호출 표면

Implementation
  - 실제 데이터 구조
  - 메모리 배치
  - 동시성 보장 범위
  - 순서/정렬/탐색 비용
  - 런타임 타입 정보 보존 여부
```

---

## 진단 포인트

- 호출하는 API가 같은지보다 내부 구현이 어떤 자료구조인지 확인한다.
- workload가 어떤 연산에 몰리는지 본다.
- 평균 성능인지 최악 성능인지 구분한다.
- 추상화가 감춘 비용이 latency, memory, GC, type information 중 어디서 드러나는지 확인한다.

---

## 트레이드오프

추상 인터페이스는 교체 가능성과 코드 가독성을 높인다. 하지만 구현 비용을 숨기므로, 성능 문제가 생기면 인터페이스 아래의 실제 구조까지 내려가야 한다.
