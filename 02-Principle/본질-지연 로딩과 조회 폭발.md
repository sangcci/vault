# Principle: 지연 로딩과 조회 폭발

**핵심 질문**: 편의를 위해 미룬 조회가 언제 성능 장애로 바뀌는가?

## 한 문장 정의

지연 로딩은 필요한 시점까지 조회를 미루는 최적화지만, 반복문 안에서 초기화되면 데이터 개수만큼 SQL 왕복이 늘어나는 구조.

---

## 해결하는 문제

- 목록 조회 API에서 연관 데이터 접근으로 SQL이 폭증하는 문제
- ORM 코드만 보고 실제 SQL 비용을 놓치는 문제
- 모든 연관관계를 EAGER로 바꿔 다른 조회를 느리게 만드는 문제

---

## 깨지는 상황

```text
조회 의도 불명확
  ↓
엔티티 목록 반환
  ↓
응답 변환 중 연관 필드 접근
  ↓
지연 로딩 N회 초기화
  ↓
SQL 왕복 폭증 / 응답 지연 / 커넥션 점유 증가
```

조회 성능은 “엔티티를 몇 개 가져왔는가”만으로 결정되지 않는다. 실제 병목은 애플리케이션 코드가 객체 그래프를 탐색하는 동안 DB와 몇 번 왕복했는지에서 드러난다.

---

## 판단 기준

- 단건 상세 조회에서 반드시 필요한 연관이면 fetch join이나 entity graph를 검토한다.
- 목록 조회에서 컬렉션을 함께 가져와야 하면 중복 row, 페이징 제약, 데이터 증폭을 먼저 확인한다.
- 단순 표시용 응답이면 DTO projection이나 별도 집계 쿼리가 더 명확할 수 있다.
- 여러 부모의 연관 데이터를 단계적으로 가져와도 된다면 batch size로 왕복 횟수를 줄인다.
- 기본 fetch 전략을 바꾸기보다 API 조회 시나리오별 로딩 계획을 명시한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| LAZY 기본값 | 불필요한 조회 감소 | 접근 시점 SQL 예측 어려움 |
| Fetch Join | 왕복 횟수 감소 | row 중복, 페이징 제약 |
| Batch Size | N개 조회를 묶음 조회로 완화 | 적정 크기 튜닝 필요 |
| DTO Projection | 응답 모양과 SQL 일치 | 객체 그래프 탐색 편의 감소 |
