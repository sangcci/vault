# Principle: 캐시 일관성과 경합

**핵심 질문**: 캐시는 언제 성능 최적화가 아니라 정합성 버그와 부하 증폭 지점이 되는가?

## 한 문장 정의

캐시는 원본 데이터의 빠른 복제본이므로, 변경 타이밍과 miss 순간의 동시 접근을 제어하지 않으면 stale data와 backend 부하 증폭이 발생한다.

---

## 해결하는 문제

- DB 업데이트 후 캐시에 오래된 값이 다시 저장되는 문제
- 캐시 만료 순간 같은 DB 조회가 동시에 몰리는 문제
- 캐시와 DB를 하나의 원자적 저장소처럼 오해하는 문제
- 평균 hit rate는 높은데 tail latency와 DB QPS spike가 생기는 문제

---

## 깨지는 상황

```text
쓰기 경로
cache evict -> DB commit
     사이에 read가 old value를 cache put
  ↓
stale cache
```

```text
읽기 경로
cache key expired
  ↓
N개 요청이 동시에 miss
  ↓
N개 요청이 같은 DB query 실행
  ↓
DB connection / CPU / lock 경합 증가
```

---

## 판단 기준

- 캐시 값은 원본 데이터가 아니라 원본의 복제본으로 본다.
- 쓰기 경로에서는 DB commit 이후 evict/put을 기본으로 검토한다.
- 읽기 경로에서는 cache miss 시 누가 원본 조회를 수행하고 나머지는 대기할지 정한다.
- 강한 일관성이 필요한 값은 캐시하지 않거나 TTL을 매우 짧게 둔다.
- stale read를 허용할 수 있는 조회 API는 soft TTL, stale-while-revalidate, background refresh를 검토한다.
- 다중 인스턴스 로컬 캐시는 서버마다 다른 값을 가질 수 있음을 전제로 설계한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| afterCommit evict | commit 전 old value 재저장 감소 | commit 이후 짧은 stale window |
| sync/request coalescing | 동시 miss 중복 조회 방지 | 대기 요청 tail latency 증가 |
| TTL jitter | 만료 spike 완화 | 만료 시점 예측 어려움 |
| stale-while-revalidate | 원본 저장소 보호, 응답 안정성 | 잠깐 오래된 값 노출 |
| 글로벌 캐시 | 인스턴스 간 중복 감소 | 네트워크/운영 비용 증가 |
