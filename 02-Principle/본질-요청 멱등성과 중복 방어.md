# Principle: 요청 멱등성과 중복 방어

**핵심 질문**: 같은 의도의 요청이 여러 번 들어와도 시스템 상태를 한 번만 바꾸려면 무엇을 기준으로 같은 요청이라고 판단해야 하는가?

## 한 문장 정의

요청 멱등성과 중복 방어는 **재시도·더블클릭·네트워크 오류로 같은 의도의 요청이 여러 번 들어와도, 서버가 요청의 동일성을 식별해 상태 변경을 한 번만 수행하고 같은 결과를 돌려주는 설계 원리**다.

---

## 해결하는 문제

이 본질은 생성 API에서 반복된다.

```text
- 주문 중복 생성
- 결제 중복 승인
- 환불 중복 처리
- 배송/출고 지시 중복 생성
- 쿠폰 중복 발급
- 예약/신청 중복 등록
```

공통 구조:

```text
client timeout / retry / double click
        ↓
같은 의도의 요청이 2번 이상 도착
        ↓
server가 동일 요청인지 판단하지 못함
        ↓
INSERT / 외부 API 호출이 반복됨
        ↓
중복 데이터 또는 중복 부작용 발생
```

---

## 깨지는 상황

중복 방어를 애플리케이션의 사전 조회에만 맡기면 동시성 창이 생긴다.

```text
T1: SELECT by business key → 없음
T2: SELECT by business key → 없음
T1: INSERT
T2: INSERT
```

프론트엔드 버튼 비활성화만으로도 부족하다.

```text
브라우저 더블클릭은 줄일 수 있음
하지만 아래는 막지 못함:
  - 모바일 네트워크 재시도
  - client timeout 후 재전송
  - proxy/gateway retry
  - 사용자의 새로고침
  - batch job 재실행
```

DB Unique Key만 있어도 중복 row는 막을 수 있지만, 재시도한 사용자에게 기존 성공 결과를 돌려주는 것은 별도 설계가 필요하다.

## 판단 기준

먼저 요청의 성격을 나눈다.

```text
같은 요청이 여러 번 와도 기존 결과를 돌려줘야 하는가?
  ├─ YES → Idempotency Key 필요
  │        예: 주문 생성, 결제 승인, 환불 요청
  │
  └─ NO  → 중복 저장만 막으면 되는가?
           ├─ YES → DB Unique Key + 예외 변환
           └─ NO  → lock / 상태 전이 / 업무 규칙 재검토
```

방어선은 한 겹이 아니라 여러 겹으로 둔다.

```text
1차: client request id / idempotency key
2차: server idempotency key 저장소
3차: DB unique constraint
4차: domain exception 변환
5차: 운영 탐지 로그/메트릭
```

Idempotency Key를 쓸 때는 request parameter도 같이 검증해야 한다.

```text
key=abc, amount=10000 → 최초 성공
key=abc, amount=20000 → 같은 key지만 다른 요청
                      → accidental misuse로 거절해야 함
```

## 트레이드오프

```text
DB Unique Key 중심
  장점: 가장 단순하고 신뢰성 높은 최후 보루
  단점: 기존 결과 반환보다 중복 오류가 되기 쉬움

Idempotency Key 중심
  장점: 재시도 UX가 좋고 외부 API와도 잘 맞음
  단점: key 저장, TTL, request hash, 결과 캐싱/조회가 필요

Lock 중심
  장점: 판단 구간을 직렬화할 수 있음
  단점: 경합 시 지연시간 증가, lock timeout, connection 점유 증가
```

중요한 결론:

```text
중복 방어의 최후 보루는 DB 제약이다.
재시도 UX까지 해결하려면 idempotency key가 필요하다.
lock은 최후 보루가 아니라 특정 경합 구간을 줄이는 보조 수단이다.
```
