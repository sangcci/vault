# Principle: 비용 기반 실행계획과 조인 전략

**핵심 질문**: 같은 JOIN 쿼리가 왜 데이터 크기와 통계에 따라 전혀 다른 성능을 내는가?

## 한 문장 정의

비용 기반 실행계획과 조인 전략은 DBMS가 같은 결과를 내는 여러 물리 실행 후보 중 통계와 비용 추정을 바탕으로 가장 싸다고 판단한 경로를 선택한다는 원리.

---

## 해결하는 문제

- JOIN 쿼리가 데이터가 늘자 갑자기 느려지는 문제
- Nested Loop, Hash Join, Merge Join을 도구 이름이 아니라 입력 조건으로 판단하는 문제
- SQL 문장 순서와 실제 실행 순서를 혼동하는 문제
- 인덱스를 추가했는데도 planner가 다른 plan을 선택하는 문제

---

## 판단 기준

```text
Nested Loop
  조건: outer 작음 + inner index 좋음
  위험: outer 커지면 loops 폭증

Hash Join
  조건: 대량 조인 + build 쪽 메모리 적재 가능
  위험: Batches > 1이면 disk spill

Merge Join
  조건: 양쪽 join key 정렬 또는 정렬 비용 낮음
  위험: Sort 비용, 중복 key mark/restore 비용
```

---

## 진단 포인트

```text
EXPLAIN ANALYZE
  ├─ estimated rows vs actual rows
  ├─ loops
  ├─ Hash Batches / Memory Usage
  ├─ Sort Method / Disk 사용 여부
  ├─ Buffers shared hit/read
  └─ Join Type 제약 LEFT/INNER
```

---

## 트레이드오프

| 전략 | 유리한 조건 | 위험 신호 |
|---|---|---|
| Nested Loop | 소량 outer, inner index | loops × inner cost 증가 |
| Hash Join | 인덱스 없는 대량 조인 | Batches > 1 |
| Merge Join | 정렬된 대량 입력 | 큰 Sort 노드 |
