# Principle: 시스템 콜과 커널 경계

**핵심 질문**: 사용자 프로그램은 왜 파일, 프로세스, 메모리를 직접 다루지 못하고 커널에 요청해야 하는가?

## 한 문장 정의

시스템 콜과 커널 경계는 사용자 공간 프로그램이 하드웨어와 전역 자원을 직접 조작하지 못하게 하고, 커널이 정해진 인터페이스를 통해 파일 I/O, 프로세스 생성, 메모리 매핑 같은 privileged operation을 대행한다는 원리.

---

## 해결하는 문제

- 사용자 프로세스가 임의로 디스크, 메모리, 다른 프로세스를 건드리는 문제
- `read`, `write`, `fork`, `execve`, `mmap`, `pipe`가 단순 라이브러리 함수처럼 보이는 문제
- 모드 전환과 문맥 교환을 혼동하는 문제
- OS 기능이 왜 시스템 콜이라는 좁은 관문으로 노출되는지 이해하는 문제

---

## 판단 기준

```text
User Space
  - 제한된 명령 실행
  - 자신의 주소 공간만 접근
  - 커널 자원 직접 조작 불가

System Call
  - user → kernel mode 전환
  - 커널이 권한 검사와 실제 작업 수행
  - 결과를 user space로 반환

Kernel Space
  - 파일 시스템, 메모리, 프로세스, 네트워크, 장치 제어
```

---

## 진단 포인트

- 성능 문제에서 syscall 빈도가 과도한지 확인한다.
- blocking syscall인지 non-blocking syscall인지 구분한다.
- syscall 호출이 항상 context switch를 의미하는 것은 아님을 구분한다.
- 파일 디스크립터, 메모리 매핑, 프로세스 생성이 어떤 kernel object를 만드는지 본다.

---

## 트레이드오프

시스템 콜 경계는 보안과 안정성을 제공하지만, mode switch와 커널 진입 비용을 만든다. 시스템 설계에서는 이 경계를 자주 넘을수록 비용이 커지고, 너무 우회하려 하면 제어와 안전성을 잃는다.
