# Principle: 단일 실행 흐름과 직렬화 비용

**핵심 질문**: 한 번에 하나만 실행하면 무엇이 쉬워지고 무엇이 막히는가?

## 한 문장 정의

단일 실행 흐름과 직렬화 비용은 하나의 실행 흐름이 작업을 순서대로 처리하면 공유 메모리 동기화 비용은 줄지만, 긴 작업 하나가 뒤의 모든 작업을 밀어내는 비용을 만든다는 원리.

---

## 해결하는 문제

- Redis, Node.js, nginx 같은 단일 이벤트 루프 모델을 “항상 빠른 구조”로 오해하는 문제
- 싱글 스레드라서 race condition이 전혀 없다고 보는 문제
- CPU-bound 작업 하나가 전체 요청을 지연시키는 문제
- 단일 실행 흐름의 원자성과 비즈니스 로직 전체의 원자성을 혼동하는 문제

---

## 판단 기준

```text
얻는 것
  - 한 순간에 한 callback만 실행
  - 공유 메모리 lock 비용 감소
  - 실행 순서 추론이 쉬움
  - context switch 감소

잃는 것
  - 멀티코어 병렬성 제한
  - 긴 작업 하나가 전체 queue 지연
  - await 경계 밖 비즈니스 원자성은 보장 안 됨
```

---

## 진단 포인트

- 단일 루프에 CPU-heavy 작업이 들어오는지 확인한다.
- callback 실행 시간이 event loop latency 예산을 넘는지 본다.
- 동일 key 작업은 의도적으로 직렬화하고 있는지, 우연히 단일 thread에 기대고 있는지 구분한다.
- 멀티 이벤트 루프/worker 확장 시 공유 상태 문제가 다시 생기는지 확인한다.

---

## 트레이드오프

단일 실행 흐름은 lock과 deadlock 부담을 줄인다. 대신 한 번에 하나만 실행하므로 CPU 작업과 긴 callback에 취약하다. 단일 스레드의 안전성은 “짧은 critical section”에 가깝고, `await`로 쪼개진 전체 usecase까지 자동으로 보호하지는 않는다.
