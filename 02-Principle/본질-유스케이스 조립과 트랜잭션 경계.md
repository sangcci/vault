# Principle: 유스케이스 조립과 트랜잭션 경계

**핵심 질문**: 트랜잭션은 어느 계층에서 열고, 비즈니스 흐름은 어디서 읽혀야 하는가?

## 한 문장 정의

유스케이스 조립과 트랜잭션 경계는 외부 요청 하나의 업무 흐름을 Application Service에서 조합하고, 그 흐름에 필요한 최소 DB 변경 구간만 트랜잭션으로 묶는 원리.

---

## 해결하는 문제

- Controller가 Repository와 Domain 세부 절차를 직접 조합하는 문제
- 트랜잭션 경계가 Repository, Domain, Helper 곳곳에 흩어지는 문제
- self-invocation 때문에 별도 트랜잭션 정책이 적용되지 않는 문제
- 외부 I/O까지 하나의 `@Transactional`로 묶어 자원을 오래 점유하는 문제
- JPA flush 예외를 어디서 비즈니스 예외로 바꿀지 불분명한 문제

---

## 깨지는 상황

```text
Controller
  ├─ repository.save()
  ├─ domain.validate()
  ├─ externalApi.call()
  └─ event.publish()

흐름 조립 위치와 transaction boundary가 흩어짐
  ↓
예외 처리 / rollback / event 순서가 불명확
```

또는 모든 것을 한 서비스 메서드에 넣는다.

```text
@Transactional
usecase 전체
  ├─ DB 조회/수정
  ├─ 외부 API
  ├─ 파일 처리
  └─ 이벤트 발행

DB connection 점유 시간이 길어짐
```

---

## 판단 기준

- Application Service는 “요청 하나를 어떤 순서로 처리하는가”를 보여준다.
- Domain/Policy는 “그 판단이 맞는가”를 담당하고, Application Service는 조립과 경계를 담당한다.
- 트랜잭션은 usecase 전체가 아니라 원자적으로 보장해야 하는 DB 변경 구간에 둔다.
- 외부 API, 파일 I/O, 알림 발송은 가능하면 트랜잭션 밖으로 분리한다.
- flush 예외를 usecase 문맥으로 바꿔야 하면 Application Service 안에서 flush 위치를 명시한다.
- 이벤트 발행은 commit 전/후 의미를 구분하고 필요한 경우 afterCommit/outbox를 사용한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| Application Service 중심 | usecase 흐름과 transaction boundary 명확 | 계층 설계 필요 |
| Domain에 흐름 조립 | 객체 응집도 증가 가능 | 외부 I/O/transaction 정책이 섞일 위험 |
| Controller 조립 | 빠른 구현 | 흐름 중복, 테스트 어려움 |
| Repository에 transaction 분산 | 단순 CRUD 편의 | usecase 원자성 파악 어려움 |
