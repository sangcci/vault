# Principle: 관측 신호의 상관관계

**핵심 질문**: 알람이 울렸을 때 어떤 신호를 어떤 순서로 연결해야 원인에 도달할 수 있는가?

## 한 문장 정의

관측 신호의 상관관계는 metrics, logs, traces를 시간·서비스·요청 식별자 같은 공통 축으로 연결해 내부 상태를 추론하는 원리.

---

## 해결하는 문제

- 대시보드 알람은 울렸지만 실제 병목 지점을 찾기 어려운 문제
- metrics, logs, traces가 각각 따로 있어 장애 대응이 느린 문제
- GC, DB connection, latency, error log 중 무엇이 원인인지 구분하기 어려운 문제
- 도구를 설치했지만 runbook 없이 매번 추측으로 대응하는 문제

---

## 깨지는 상황

```text
metrics: p99 latency spike
logs: ERROR 증가
traces: 일부 span 지연
GC: pause 증가
DB: connection usage 증가

공통 축 없음
  ↓
같은 장애의 원인/결과인지 판단 불가
```

관측 데이터는 많이 모으는 것보다 서로 이어서 읽을 수 있어야 한다.

---

## 판단 기준

- metrics는 증상 감지와 규모 파악에 사용한다.
- logs는 사건 맥락과 예외 원인을 확인하는 데 사용한다.
- traces는 요청 경로와 구간별 지연을 확인하는 데 사용한다.
- 모든 신호는 최소한 `service`, `instance`, `endpoint`, `status`, `traceId` 같은 공통 축을 공유해야 한다.
- JVM 문제는 heap used, GC pause, allocation rate, CPU, thread, request latency를 같은 시간축에서 본다.
- label cardinality가 과도하게 커지면 저장 비용과 쿼리 비용이 폭증하므로 주의한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| metrics 중심 | 빠른 감지, 낮은 저장 비용 | 개별 요청 맥락 부족 |
| logs 중심 | 사건 상세 확인 | 전체 추세와 수치 집계 약함 |
| traces 중심 | 병목 구간 파악 | 샘플링/전파/저장 비용 |
| 공통 label 표준화 | 신호 연결 쉬움 | label cardinality 관리 필요 |
| 긴 보관 기간 | 사후 분석 가능 | 저장 비용 증가 |
