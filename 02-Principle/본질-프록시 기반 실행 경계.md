# Principle: 프록시 기반 실행 경계

**핵심 질문**: 어노테이션이 붙어 있는데도 왜 부가 기능이 실행되지 않는가?

## 한 문장 정의

프록시 기반 실행 경계는 부가 기능이 target 객체 내부가 아니라 proxy를 통과하는 호출 지점에서만 적용된다는 원리.

---

## 해결하는 문제

- 같은 클래스 내부 호출로 트랜잭션이나 캐시가 적용되지 않는 문제
- `@Transactional`, `@Cacheable`, `@Async`가 어노테이션만 붙이면 항상 동작한다고 오해하는 문제
- AOP를 코드 변환이 아니라 호출 경로 제어로 이해해야 하는 문제

---

## 깨지는 상황

```text
외부 호출
caller → proxy → advice → target
                 ✅ 적용

내부 호출
target.outer() → this.inner()
                 ❌ proxy 우회
```

프록시 방식에서는 호출자가 proxy를 바라볼 때만 advice가 실행된다. target 내부의 `this`는 proxy가 아니라 실제 target 자신이다.

---

## 판단 기준

- AOP 기반 기능이 필요한 메서드는 외부 Bean에서 호출되도록 경계를 나눈다.
- 같은 클래스 내부 호출에 `@Transactional`, `@Cacheable`, `@Async`를 기대하지 않는다.
- 내부 단계에 별도 transaction/cache/async 정책이 필요하면 Bean을 분리하거나 명시 API를 사용한다.
- 문제 해결을 위해 self injection을 쓰기 전, usecase 경계가 잘못 잡힌 것은 아닌지 먼저 본다.
- proxy 기반 AOP로 해결하기 어려우면 AspectJ weaving이나 programmatic API를 검토한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| Spring proxy AOP | 설정 단순, Bean 모델과 통합 | self-invocation 제약 |
| Bean 분리 | 호출 경계 명확 | 클래스 수 증가 |
| TransactionTemplate | 경계 명시적 | 선언형보다 코드 증가 |
| AspectJ weaving | 내부 호출도 advice 가능 | 빌드/런타임 설정 복잡 |
