# Principle: 부하 평탄화와 버스트 허용

**핵심 질문**: 요청을 평균 속도로 제한할 것인가, 순간 폭증을 어느 정도 허용할 것인가?

## 한 문장 정의

부하 평탄화와 버스트 허용은 시스템이 감당할 수 있는 장기 평균 처리율과 순간 폭증 허용량을 분리해 요청을 통과·대기·거부하는 원리.

---

## 해결하는 문제

- API Rate Limit을 걸었는데 정상 사용자의 순간 요청까지 막히는 문제
- Token Bucket과 Leaky Bucket을 상황에 맞게 고르지 못하는 문제
- 평균 TPS만 보고 burst size를 설계하지 않는 문제
- 분산 서버에서 rate limit 카운터가 인스턴스별로 흩어지는 문제

---

## 판단 기준

```text
정상 사용자의 짧은 burst를 허용해야 하는가?
  → Token Bucket

downstream 처리율을 일정하게 보호해야 하는가?
  → Leaky Bucket

초과 요청을 기다리게 할 수 있는가?
  → queue / delay 가능

초과 요청은 즉시 실패해야 하는가?
  → 429 + retry-after

여러 app instance가 같은 제한을 공유해야 하는가?
  → Redis / gateway / centralized limiter
```

---

## 알고리즘 감각

```text
Token Bucket
  - 토큰이 일정 속도로 채워짐
  - 토큰을 모아두면 순간 burst 통과
  - UX 친화적 API 제한에 적합

Leaky Bucket
  - 큐에서 일정 속도로만 출력
  - 입력 burst를 평탄화
  - downstream 보호/QoS에 적합
```

---

## 트레이드오프

버스트를 허용하면 정상 사용자 경험은 좋아지지만, 순간 부하가 downstream에 전달된다. 부하를 평탄화하면 downstream은 안정되지만, 사용자는 지연이나 거부를 경험할 수 있다. Rate Limit은 숫자 하나가 아니라 평균 속도, burst 크기, 대기 정책, 공유 상태 범위의 조합이다.
