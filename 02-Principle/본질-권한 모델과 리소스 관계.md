# Principle: 권한 모델과 리소스 관계

**핵심 질문**: 이 사용자가 이 기능을 쓸 수 있는가와 이 리소스를 다룰 수 있는가는 왜 다른 질문인가?

## 한 문장 정의

권한 모델과 리소스 관계는 사용자 역할만으로는 리소스별 소유권·조직·멤버십 관계를 표현할 수 없으므로, RBAC 같은 정적 권한과 DAC/ReBAC 같은 객체 관계 검증을 함께 사용해야 한다는 원리.

---

## 해결하는 문제

- ROLE_USER만 확인하고 남의 리소스 수정이 가능한 문제
- 관리자/사용자 role만으로 모든 인가를 표현하려는 문제
- 목록 필터와 단건 권한 검증이 불일치하는 문제
- 회사 보안 구조에서 MAC/RBAC/DAC 레이어를 구분하지 못하는 문제

---

## 판단 기준

```text
MAC
  - 조직/시스템이 강제하는 절대 정책
  - 예: SCP, 리전 제한, 서비스 금지

RBAC
  - role 기반 기능 권한
  - 예: ADMIN만 관리자 페이지 접근

DAC / Ownership
  - resource owner가 누구인가
  - 예: 내 예약만 수정 가능

ReBAC
  - user-resource 관계 그래프
  - 예: 프로젝트 maintainer만 배포 가능
```

---

## 진단 포인트

- API가 기능 권한과 객체 권한을 모두 확인하는지 본다.
- tenantId/userId/organizationId 조건이 쿼리와 검증에 모두 들어가는지 확인한다.
- default allow가 아니라 deny-by-default인지 확인한다.
- 권한 정책이 controller, service, repository에 흩어져 있지 않은지 본다.
- 권한 테스트에 다른 사용자/다른 tenant negative case가 있는지 확인한다.

---

## 트레이드오프

RBAC는 단순하고 관리하기 쉽지만 동적 관계 표현이 약하다. ReBAC는 정확하지만 쿼리와 모델 복잡도가 커진다. 작은 서비스는 RBAC + ownership check로 시작하고, 관계가 복잡해질수록 policy/service로 분리한다.
