# Principle: 캐시 키 공간과 참조 지역성

**핵심 질문**: 어떤 조회는 캐시해도 왜 hit rate가 오르지 않는가?

## 한 문장 정의

캐시는 같은 key가 반복 조회될 때만 효과가 있으므로, key 공간이 무한히 커지는 동적 조회는 참조 지역성을 만들지 못해 캐시 효율이 무너진다.

---

## 해결하는 문제

- 동적 검색 조건을 캐시해도 적중률이 오르지 않는 문제
- `@Cacheable`을 붙였는데 메모리만 늘고 DB 조회가 줄지 않는 문제
- 캐시 대상을 “느린 쿼리” 기준으로만 고르는 문제
- 목록 캐시와 개별 객체 캐시의 무효화 단위를 섞는 문제

---

## 깨지는 상황

```text
검색 API 파라미터
keyword × sort × page × filter
  ↓
캐시 key 조합 폭발
  ↓
대부분의 key가 1회 접근
  ↓
cache hit ≈ 0%
  ↓
메모리 사용량 증가 + eviction 증가 + DB 부하 유지
```

캐시의 핵심은 저장 속도가 아니라 반복 접근이다. 같은 데이터를 담더라도 key가 다르면 캐시 입장에서는 다른 엔트리다.

---

## 판단 기준

- 캐시 적용 전 key cardinality를 추정한다.
- 같은 key가 반복 접근되는 정형 쿼리인지 확인한다.
- 키워드 검색, 다중 필터, deep paging은 로컬 캐시보다 검색 엔진/쿼리 최적화를 먼저 검토한다.
- 정렬 조건만 다르면 key에서 제외하고 애플리케이션에서 정렬 가능한지 본다.
- 변경 빈도가 낮고 트래픽이 몰리는 첫 페이지, 상위 N개, 설정성 데이터는 캐시 후보로 본다.
- 캐시 이름과 key는 무효화 단위에서 역산한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 정형 쿼리 캐시 | 높은 hit rate, 단순 운영 | 적용 범위 제한 |
| 동적 검색 캐시 | 구현은 쉬움 | key 폭발, 낮은 hit rate |
| key 정규화 | 중복 엔트리 감소 | 후처리 로직 필요 |
| 개별 객체 캐시 | 정밀 무효화 | 목록 조립 비용 증가 |
| 리스트 캐시 | 구현 단순 | 일부 변경 시 전체 무효화 |
