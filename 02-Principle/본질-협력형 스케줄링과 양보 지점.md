# Principle: 협력형 스케줄링과 양보 지점

**핵심 질문**: async/await와 coroutine은 언제 다음 작업에게 실행권을 넘기는가?

## 한 문장 정의

협력형 스케줄링과 양보 지점은 OS가 임의로 끊는 선점형 스케줄링과 달리, coroutine/task가 `await`, `yield`, `suspend` 지점에서 스스로 제어권을 반납할 때만 다른 작업이 실행된다는 원리.

---

## 해결하는 문제

- 싱글 스레드 이벤트 루프인데도 `await` 사이에 다른 요청이 끼어드는 문제
- CPU-bound coroutine이 yield하지 않아 전체 루프를 막는 문제
- `await`가 단순 대기 문법이 아니라 원자성 경계라는 점을 놓치는 문제
- callback, promise, coroutine을 실행 모델이 아니라 문법 차이로만 보는 문제

---

## 판단 기준

```text
선점형 스케줄링
  - OS timer interrupt가 실행권을 회수
  - thread 단위로 강제 교체 가능

협력형 스케줄링
  - task/coroutine이 await/yield/suspend에서 양보
  - 양보하지 않는 CPU 작업은 계속 루프를 점유
```

`await`의 두 얼굴:

```text
성능 관점
  I/O 대기 중 thread를 묶지 않고 다른 작업 실행

정합성 관점
  로직이 중간에 끊기고 다른 작업이 끼어들 수 있는 경계
```

---

## 진단 포인트

- 긴 CPU loop 안에 yield 지점이 있는지 확인한다.
- read-modify-write가 await 전후로 나뉘는지 본다.
- task cancellation 시 중간 상태가 남는지 확인한다.
- coroutine dispatcher/event loop가 단일 thread인지, thread pool 위에서 동작하는지 구분한다.

---

## 트레이드오프

협력형 스케줄링은 OS context switch를 줄이고 비동기 코드를 자연스럽게 표현한다. 하지만 작업이 스스로 양보하지 않으면 공정성이 깨지고, 양보 지점은 비즈니스 원자성이 끊기는 경계가 된다.
