# Principle: 연관 방향과 변경 경계

**핵심 질문**: 객체가 서로를 참조해도 되는 범위는 어디까지인가?

## 한 문장 정의

연관 방향은 탐색 편의가 아니라 변경 책임, 조회 시나리오, 외부 노출 경계를 기준으로 정해야 하는 객체 그래프 설계 원리.

---

## 해결하는 문제

- 양방향 연관관계가 JSON 직렬화에서 순환 참조로 터지는 문제
- 조회 편의만 보고 양방향을 열었다가 N+1과 API 스키마 누수가 생기는 문제
- 단방향만 고집해 필요한 조회마다 불필요하게 복잡한 쿼리를 작성하는 문제

---

## 깨지는 상황

```text
탐색 편의만 보고 양방향 설정
  ↓
Entity를 Controller에서 직접 반환
  ↓
Post → Comment → Post 재귀 직렬화
  ↓
StackOverflowError / 500 응답
```

또는 다음처럼 변경 경계가 흐려진다.

```text
Order ↔ OrderItem
  ↓
양쪽에서 마음대로 컬렉션 수정
  ↓
연관관계 주인, cascade, orphanRemoval 판단이 섞임
```

---

## 판단 기준

- 반대 방향 탐색이 실제 유스케이스에 있고, 같은 aggregate 안에서 변경 규칙을 관리할 수 있으면 양방향을 검토한다.
- 단순 조회 편의만 필요하면 repository query, DTO projection, fetch join으로 해결할 수 있는지 먼저 본다.
- Controller 응답에는 Entity를 직접 내보내지 말고 DTO로 외부 경계를 끊는다.
- 양방향을 쓰더라도 연관관계 편의 메서드로 변경 지점을 한곳에 모은다.
- Cascade와 orphanRemoval은 “부모가 자식 생명주기를 소유하는가”를 기준으로 제한한다.

---

## 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 단방향 | 객체 그래프 단순성, 직렬화 위험 감소 | 반대 방향 탐색 시 쿼리 필요 |
| 양방향 | 도메인 탐색 편의, 일부 쿼리 단순화 | 순환 참조, 변경 경계 혼란, 로딩 비용 노출 |
| DTO 경계 | API 안정성, 순환 차단 | 매핑 코드 증가 |
