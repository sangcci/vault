# 요구사항과 정책 그리고 명세를 구분하자

평소 이 3단어를 혼용해서 햇갈렸다. 
- 요구사항 -> 무엇, 왜
- 정책 -> 기준, 제약
- 명세, 스펙 -> 시스템 행동

- 고객이 결제한 주문을 취소할 수 있어야 한다.
- 배송 준비 전까지만 취소할 수 있고, 미리 사용한 쿠폰은 복구하지 않는다.
- 취소 요청 시 주문 상태를 검사하고, 결제 취소가 성공하면 주문 상태를 `CANCELED`로 바꾼다. 결제 취소에 실패하면 주문 상태를 유지한다. 요청 경로나 인증 방식, 응답 필드와 오류 코드 JSON 예시를 준다.

세 단어 사이의 의미 차이도 중요하지만, 각 단어의 "힘"의 차이를 인지해야 한다.
정책도 "어느정도" 정하고, 백엔드 부서에서 한번 더 체크해서 "결정된" 정책으로 성장한다.
명세 또한 "어느정도" 정하고, 백엔드 부서에서 마찬가지로 한번 더 체크하여 "구현가능한" 명세로 성장한다.

요구사항을 들으면 우리는 기준과 제약 그리고 시스템이 어떻게 행동하면 될지를 파악한다. 기획팀과 논의해 기술적으로 불가능한 부분 혹은 이렇게 구현하면 더 좋다는 등의 의견 피력도 이 단계에서 나오는 거라 정말 중요하다.
