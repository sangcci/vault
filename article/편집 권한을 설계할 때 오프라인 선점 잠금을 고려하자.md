# 편집 권한을 설계할 때 오프라인 선점 잠금을 고려하자
동시 수정 구현을 figma처럼 동시에 접속해서 실시간으로 반영하는 구조로 할 수 있지만, 초기에 설계하기 어렵고 운영 난이도가 크다.

"수정하기" API 요청에 한해서 동시성을 고려하면,
- 한 사용자가 10개 이상의 필드를 손수 수정하고 수정하기 버튼을 눌렀는데 실패하게 될 경우, 불쾌감을 느낀다.
- 반대로 이미 이전에 수정하기 버튼을 눌렀는데, 그 시점에 다른 사용자가 수정하기 버튼을 거의 같은 타이밍에 눌러서 내가 수정한 내역이 반영되지 않는다.
실패했을 때의 처리를 어떻게 하느냐에 따라 위 상황 중 1개는 무조건 발생하게 된다.

이런 상황을 방지하기 위해 미리 편집 권한을 획득하는 방법이 있다. 이를 "오프라인 선점 잠금"이라 부른다.

이를 적용하면, 실제 DB 락은 걸지 않으면서 자연스럽게 잠금의 역할을 수행할 수 있다.

구현 방법은 여러 가지가 있다.
- DB 내 각 도메인 테이블 내 `expired_at`, `token` 등 컬럼 추가
- DB 내 별도 락 테이블 구성
- Redis 등 외부 서비스 활용 락 구성

이중에서 만약 DB가 1개로 활용되고 있고, 단일 서버로 이루어진 초기 단계라면, DB를 그대로 이용하는 방법이 구현하기 쉽다.
