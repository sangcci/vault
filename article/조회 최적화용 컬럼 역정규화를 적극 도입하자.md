# 조회 최적화용 컬럼 역정규화를 적극 도입하자

기존에는 이런 부분들을 인지하지 못한 상태에서 AI가 추천해준 대로 진행.

밑의 이 2가지를 구분하면 역정규화에 대해서 쉽게 인식하고, 다른 프로젝트에서도 정책과 비교해 쉽게 알아낼 수 있을거라 생각.

- 정책의 원천 상태 - status, deletedAt, expiresAt, ownerId
- 조회 최적화용 인위적인 값 - searchable, visibilityStatus, searchCategory

조회 최적화 용도로 컬럼을 추가하는 경우, 이렇게 정책에 꼭 필요한 원천 데이터와 인위적으로 우리가 만든 값을 분리해서 인식하는게 중요.

그 이후로 조회 로직을 볼 때 불필요하게 많은 `WHERE`절이 있다면 고려. 실제 SQL 실행 계획도 보면 불필요한 JOIN 및 필터링을 구성하는 경우가 대부분. 즉, 쿼리 최적화 측면에서도 제대로 이뤄지지 않을 가능성 농후.

상태를 변경하는 usecase에서 해당 값 까지 update할 수 있다면 도입.

조회 쿼리를 구성하는게 쉬워진다.

> 실행계획을 살펴보고, 조회 로직의 복잡성도 살펴보자.
