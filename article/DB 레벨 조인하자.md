# DB 레벨 조인하자

## 배경

어플리케이션 레벨 조인 vs DB 레벨 조인. 

조회 로직을 구현할 때 한 조회 usecase 당 SQL문을 통째로 만들어 구현할지, 
도메인 Bounded Context로 구분해 어플리케이션 단에서 조합할지

첫번째는 QueryDsl 혹은 JOOQ등 SQL을 직접 다뤄서 바로 DTO 모델에 매핑
두번째는 JPA 등 ORM 기술을 활용해 Domain을 조회해 조합하는 방식

## 무엇을 선택해야 할까?

기능 구현에 앞서, 요구사항 명세와 화면 디자인을 보고 어떻게 구현할지 구상함.

현재 서버 아키텍처를 보고 결정해야 할듯. 
단일 DB라면, 일관성 문제도 없을 것이니 domain 경계를 넘나들며 SQL로 JOIN해도 된다고 생각함. 

도메인 경계를 넘나드는 것이 유지보수 측면에서 딱히 단점은 없다고 생각함. usecase 안에 다른 domain들이 많아지는 것을 경계하면 안됨. 어떻게 생각해보면 당연한 일임. 헥사고날 아키텍처를 이론으로 공부해보다 생긴 단점임.

만일 domain 별로 서버가 분리되어 있고, MSA 구조로 domain도 각 repo마다 따로 구현되어 있으면 유지보수 측면에서 불리할 수 있음. 같은 domain인데 여러 repo에 퍼져 있다보니, 한 번 수정할 때 마다 다 수정해야 함. 근데 단일 DB면 멀티 모듈로 구성한다면 이 단점은 생기지 않을 것 같음.

DB 또한 분리되어 있다면 선택의 여지가 없음. 어플리케이션 레벨에서 조인할 수 밖에 없음. 이 때는 조회에 필요한 조건을 가지고 있는 domain 영역에서 필터링을 거쳐서 나머지 데이터를 가져올 때는 외래키 혹은 Id 값으로 조회하는 것을 선호.
