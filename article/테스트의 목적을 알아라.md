# 테스트의 목적을 알아라

- Verification — 지금 구현이 요구사항대로 동작하는가
- Regression Safety — 기존 동작이 변경 때문에 깨지지 않았는가 > 리팩토링 및 마이그레이션에 필수로 요구
- Specification — 시스템이 어떤 동작을 해야 하는가
- Design Feedback — 코드 구조와 책임 분배가 적절한가
- Documentation — 이 코드를 어떻게 사용하고 어떤 행동을 기대해야 하는가

무엇을 검증할까?

```
Business / Domain
│
├── 정책
├── 상태 전이
├── 계산 규칙
└── invariant

Application
│
├── Use Case 흐름
├── orchestration
├── transaction
└── dependency interaction

Infrastructure
│
├── DB mapping
├── Query
├── 외부 API
├── Message Broker
└── Serialization

Interface
│
├── HTTP contract
├── Validation
├── Authentication
└── Error response

System
│
├── 사용자 시나리오
└── End-to-End
```

어느 범위까지 같이 실행할까?
```
작은 범위                           큰 범위

Unit
 │
 ├──── Component
 │
 ├──────── Integration
 │
 └──────────────── E2E

빠름 ───────────────────────→ 느림
격리 ───────────────────────→ 실제 환경
```

하지만 정책 테스트 = 단위 테스트 라고 항상 볼 수 있는 것도 아니고, Service 테스트 = 통합 테스트 인 것도 아님.
