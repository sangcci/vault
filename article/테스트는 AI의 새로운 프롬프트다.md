# 테스트는 AI의 새로운 프롬프트다

기존에 테스트는 코드 아키텍처를 지키게 만들고, 기능이 잘 돌아가는지 검증하는 것이었다면, AI Agent 시대에 테스트는 맥락 그 자체로 활용할 수 있다.

AI Agent가 프로젝트를 이해하기 위한 수단으로 몇가지를 뽑으면,
- 글로 정리한 문서
- 코드
- 코드 주석
- README.md, AGENTS.md 등 Agent 지침서
- 테스트 코드
- ...

하지만 매번 문서로 저장해서 관리하기에는 너무 많은 리소스가 소모된다. 문서 관리까지 AI에게 맡기면 AI의 이상한 문체 때문에 매번 글을 읽고 이해하기 어렵다.

지침으로 관리하기에는 도메인 정책 및 아키텍처 결정 하나하나를 글로 관리할 수 없다.

소스 코드는 어떻게 처리하는지는 알려주지만, 그걸 "왜" 구현했는지는 보여주지 못함. 또한 경계를 보여주기에도 상당한 제한이 존재.

테스트 코드 자체가 하나의 ADR이 될 수 있음. 
- `@DisplayName()`으로 왜 테스트를 구성해야 하는지 알 수 있음
- `given-when-then`으로 입력 조건들과 기대 결과들을 볼 수 있음
- 실패 케이스로 어떤 경우에 실패가 발생하는지 알 수 있음

예를 들어, AI Agent는 현재 소스 코드만 보면 현재 구현이 어떻게 되어있는지만 볼 수 있다.
하지만 다음 테스트들이 추가로 마련되어 있다면,
```java
changePassword_success()
samePassword_cannotBeUsed()
withdrawnUser_cannotChangePassword()
passwordShorterThan8Characters_isRejected()
```
AI가 얻는 정보는,
```
              Production Code
                    │
                    ↓
             현재 어떻게 동작하는가

Tests
 │
 ├── success
 │      ↓
 │   무엇을 허용하는가
 │
 └── negative
        ↓
     무엇을 거부하는가

              ↓

       Behavioral Contract
```

> 누군가 변경하면서 bug를 넣었을 때 test suite가 이를 탐지하는 역할

물론 구조적 결정이나 "왜" 구현했는지 함수 단위를 넘어서는 담기 어렵다는 것은 한계점으로 남는다. 그래서 결국 인간이 직접 검증하는게 필요.





DCI 패턴이라던지 이런 것을 지키는 것보단, 우리가 진짜 필요로 하는 패턴을 적용하는게 맞는거 같음. DCI 패턴을 지키지 않아도 각 정책의 테스트를 잘 보여준다면 오히려 간결하고 좋음.

테스트 코드의 이름은 인간이 직접 구성하고 AI에게는 해당 구현 코드를 작성하게 지침하는게 좋을듯 하다.

negative test case를 작성하자. negative test case가 시스템의 경계를 보여준다.
- "정책 상 양수 보관 일수를 허용한다"
- "정책 상 음수 보관 일수를 허용하지 않는다"

"소셜 로그인 X는 검토했지만 제품 범위에서 제외했다" 같은 결정은 ADR/Jira가 적당.
